# 斗破战斗模块 + PVP 深度调研与设计方案（供评估）

- 版本：v1.0
- 时间：2026-11-16 16:11 GMT+8
- 状态：**调研与方案评估稿，尚未写任何产品代码**
- 目标：为「着重开发战斗模块、新增 PVP 战斗」提供决策依据，先评估再动手

---

## 0. 一句话结论

现有战斗内核（`core.fight` / `core.duel`）已经是**纯函数、数据驱动、带完整状态效果**的成熟回合制引擎，
`duel()` 本质上就是一个**现成的双人 PVP 模拟器**（只差结算与匹配）。
因此 PVP 不该重写战斗，而应：
**① 抽象出「统一战斗内核」消除 fight/duel 重复 → ② 在内核之上加 PVP 竞技层（ELO 匹配 + 公平性 + 奖惩）→ ③ 复用现有战报/卡片做展示。**
行业最新方向（2024-2026）是「确定性模拟 + 数据驱动 + 表现/逻辑分离」，本项目已天然满足大半，补齐短板即可。

## 1. 现状剖析（第一手代码事实，已逐行核实）

### 1.1 数据模型

**玩家战斗相关字段（player dict）**
| 字段 | 含义 | 出处 |
|---|---|---|
| `lv` | 等级 | `core.create_player` |
| `hp` / `mp` | 当前气血 / 斗气 | `fight()` 战后回满 mp |
| `weapon` | 武器强化等级（0~10） | `stats()` 加算词条 |
| `bonus` | 额外属性加成 dict | `stats()` 加算 |
| `flames` | 异火等级 dict（5 种） | 被动加成 / 主动技 |
| `learned` / `skills` / `loadout` | 已领悟 / 技能等级 / 四槽 | 技能系统 |
| `faction` / `faction_name` | 宗门 | 宗门传承加成 |
| `wins` / `losses` | 战绩 | `fight()` 胜负累加 |
| `bag` / `gold` / `exp` / `药渣` | 资源与物品 | 背包系统 |

**六维属性（`stats()` core.py:91）**：力量 / 敏捷 / 斗气 / 防御 / 体力 + 机缘
- 基础值按等级成长（`c_stat`），玄重尺 4 词条加算，异火「帝炎」全属性 ×1.2
- 派生：`power()` 战力（core.py:147）= 力量×2.0 + 敏捷×1.5 + 斗气×1.2 + 防御×1.5 + 体力×0.2 + 武器×200
- `mp_max()` 斗气槽 = 斗气×2×(1+0.25×青莲地心火等级)
- `dodge_rate()` / `crit_rate()` 闪避/暴击（%，上限 80），受敏捷、异火、bonus 影响

**战报条目（log list，每个 dict）**——这是展示层契约，PVP 必须兼容：
| kind | 含义 | 关键字段 |
|---|---|---|
| 出手（技能名） | 普攻或技能命中 | `who`(duel), `dmg`, `skill`, `crit`, `notes`, `heal_ratio` |
| `持续伤害` | DoT | `dmg`, `dot=True`, `notes` |
| `反伤` | 反弹 | `dmg`, `reflect=True` |
| `闪避` / `被控` | 未命中/被眩晕 | `dmg=0`, `miss=True` |
| `兽击` | PVE 怪物反击 | `dmg`, `taken=True` |

> 曾因战报渲染硬取 `it['crit']` 遗漏特殊条目导致战斗回包崩溃（2026-11-16 已修为 `it.get`）。
> PVP 战报必须沿用「特殊条目字段不齐全」的鲁棒约定。

### 1.2 战斗核心

- **`fight(p, mon, rng)` core.py:552**：PVE，15 回合上限；玩家随机放已上阵且斗气够的技（ `_pick_skill` ），
  怪物按 `monster_scaled` 实例化反击；斗气每战回满、战后不结转；胜负后结算 exp/gold/掉落/战绩。
- **`duel(p, vic, rng)` core.py:643**：**双人互殴**——双方各用四槽随机出手（p 先手），
  支持 DoT/控制/反伤/吸血，战报带 `who` 区分双方。**刻意不改 hp/gold**，结算交给 `commands.cmd_rob`（掠夺）。
  这就是现成的 PVP 战斗模拟器。
- **`damage_schedule()` / `cum_damage()` core.py:248**：逐回合期望输出模拟（含暴击期望），
  原用于反解同阶怪血量（TTK 设计），可直接用于 PVP 平衡校验。
- **伤害公式（`_hit` core.py:~380）**：`(力量×0.5 + 斗气×1.5) × 技能倍率`，减伤 `mitigation(防御)`，
  暴击期望、异火吸血。

### 1.3 物品 / 技能 / 状态效果

- **技能**：`skill_book.py` 185 门斗技（阶位/类型/范围/效果 effects/出处），`skills.py` 三阶四槽 + 斗气单价，
  `skill_up()` 升级。技能效果 `effects` 是声明式 dict（如 `{'t':'stun','p':0.25,'d':1}`）。
- **状态效果引擎**：`skill_effects.py` 的 `fx.new_state()` / `on_turn_start`(DoT/控制) / `on_incoming`(减伤/反伤) /
  `expire_turn`。**fight 与 duel 各用 2 份状态**，纯函数、可单测。
- **异火**：`flame_skills.py` 提供主动技/被动技，`fight` 里以吸血/闪避/暴击/经验加成形式介入。
- **物品**：`add_item` / `count_item` / 武器强化（`enhance`）/ 药品（服丹回血）；战斗内物品仅「药渣喂养异火」，
  **尚无「战斗中嗑药」机制**（可作为 PVP 战术深度候选）。

### 1.4 架构优点与约束

**优点**
- 战斗核心（`core.py` / `skills.py` / `skill_effects.py` / `config.py`）**零 nonebot 依赖**，纯函数 + 注入 `rng` → 可复现、可单测（现有 7 套 runner 全绿）。
- 战报结构化、展示层（commands/card）与逻辑层分离。
- `rng` 注入 = 确定性模拟的天然基础（行业最新方向的核心）。

**约束 / 短板**
- `fight` 与 `duel` 大量重复（回合循环、DoT、控制、反伤），维护双份 → 应抽象统一内核。
- 无「行动选择」：技能随机释放，玩家无战术输入 → PVP 若沿用会变成纯数值比大小（行业公认为PVP大忌）。
- 无 PVP 竞技层：无匹配、无积分、无公平性保护、无正式口令/奖惩。
- 无「战斗中道具」「先手/速度」「属性克制」等深度维度（可选增强）。

### 1.5 PVP 现状结论

**没有任何正式 PVP 系统**，但有 3 个可直接复用的底座：`core.duel()`（战斗）、`power()`（战力）、
`damage_schedule()`（平衡模拟）。现有「抢/掠夺」是PVP雏形但**无积分、无公平匹配、会造成真实金币损失**。

## 2. 行业调研（纯文本/MUD 游戏战斗设计）

### 2.1 经典 MUD 的战斗范式（来源：mud.nisfeb.com/research/05-mud-game-design、MUD-Dev 档案、Grokipedia）

- **属性模型**：D&D 六维（STR/INT/WIS/DEX/CON/CHA）→ 派生命中/伤害/护甲/豁免/HP/MP。
  多轴成长（等级/训练点/技能练习/声望点）比单条等级线更耐玩。
- **回合制（DikuMUD tick）**：进入战斗 → 每 tick 自动攻击 → 可用技能/法术 → 直到死亡/逃跑/被救。
  「自动普攻 + 玩家择机放特技」是主流。
- **敌人 AI**：aggro（见人就打）/ assist（帮同伴）/ wander / sentinel / scavenger；Lua 脚本做复杂行为。
- **PVP 五流派**：Open PK / 双方同意 PK / 公会 PK / 竞技场 PK / 行为标记（偷窃后变可攻击）。
- **死亡惩罚光谱**：尸体跑尸 / 掉经验 / 掉金币物品 / 时间锁 / 无惩罚（休闲友好）。

### 2.2 回合时序的「五阶段黄金分割」（来源：CSDN MUD 战斗内核实战）

每回合严格分 5 阶段，职责单一、便于调试：
① 状态刷新（Buff 时长-1、到期移除）→ ② 行动选择（解析指令、校验可用）→ ③ 效果结算（伤害/Buff/连招）→
④ 事件广播（死亡等事件，不改状态）→ ⑤ 输出渲染（批量写日志）。
**数值平衡三锚点验证法**：PVE 3~5 回合 / PVP 6~8 回合击杀标准敌人；资源周转率 0.95~1.05；
连招达成率用 10000 次模拟统计。**用自动化脚本验证，拒绝「我觉得这个CD挺合理」的主观判断。**

### 2.3 工业级战斗内核（MudForge / jasona-gameweaver，combat.ts 1783 行，来源 DeepWiki）

- 集中式 `CombatDaemon`，每对战斗一个 `CombatEntry`（attacker/defender/roundCount/nextRoundTime）。
- **变长期回合**：`roundTime = BASE(3000ms)/max(0.5,1+attackSpeed+weaponSpeed) − (DEX−10)/5×100ms + 负重惩罚`，钳制 1000~5000ms。
- **命中**：`75 + toHit + (DEX−10)×2 + LUCK/10 − toDodge − (DEF_DEX−10)×2 + 等级差`，钳制 5%~95%；打高级每级−2%(上限−30%)，打低级每级+1%(上限+15%)。
- **闪避/招架/格挡/暴击/反击/绕圈** 各有独立公式与上限；暴击 +100% 伤害且**穿透护甲**；格挡减伤 50%。
- **8 类状态效果**：stat_modifier / combat_modifier / DoT / HoT / stun / invulnerable / thorns(反伤) / damage_shield，每心跳 tick、可叠层、有上限。
- **仇恨系统**：法术伤害仇恨高于物理，治疗仇恨低，潜行影响最终仇恨。
- **PVP 权限**：配置开关 `combat.playerKilling`，普通玩家不能打管理员，宠物受保护。

### 2.4 迷你 MUD 数值模型（52mud.com，中文实战）

`hp/mp/ap/pp/dp/mv` 六资源，`hp=((x_hp/10)^4 + x_hp^2 + con^2)×(100+加成)/100`，
`damage=(a×mp/10 + b×str² + c×weapon)×伤害系数`；出招受 mv（行动点）/mp（法力）限制——
**「力气用光只能挨打」**是经典资源管理张力。

### 3.3 PVP 竞技系统设计（来源：duskmaw.com DevLog、Birdor 博客、StraySpark、discords.sbs）

**ELO 实战参数（VvW 浏览器 MMO，纯数值战斗，与本项目场景最贴近）**
- 初始 ELO 1000；K 因子：≤20级=32，>20级=16；**攻击范围限制 ±400 ELO**（服务端硬校验，杜绝高玩虐菜）；
- 每个目标每天最多打 3 次（滚动 24h 窗口）；ELO 地板 600；
- 新手保护：建号 72h 内不可被攻击（但可主动攻击）；被击败后 2h 保护；
- 抢金币上限 10~25%；ELO 与角色等级解耦（优化良好的低级角色也能高 ELO）。

**评分系统选型**：1v1 用 ELO 或 Glicko-2；团战用 TrueSkill2；
现代做法是「隐藏 MMR（用于匹配）+ 可见段位（提供成长感）」双层。
**回合制 PVP 的核心难题**：无操作技巧表达时，数值差距完全主导 → 必须靠公平匹配 + 战术选择（同时出招/技能组合）来补。
discords.sbs 的 PVP 采用**同时回合制**（双方同时选行动，结算前互不知晓），支持 Attack/技能1/技能2/Defend/Ultimate，ELO 计分——**最适合文字机器人的 PVP 交互范式**。

### 3.4 最新设计方向总结（2024-2026）

1. **确定性模拟 + 种子化 RNG**：同一 seed 战斗可完全重放 → 可自动化测试平衡、反作弊、lockstep（FRONTIDE / SpaceAutoBattler / ryuis-gamecore）。
2. **数据驱动**：技能/Buff/属性配表化（Excel/JSON），策划不改代码即可迭代（EGamePlay）。
3. **逻辑/表现分离**：战斗核心无渲染依赖，可服务端跑、可单测（EGamePlay、SpaceAutoBattler、ryuis-gamecore 共同强调）。
4. **声明式效果 + 钩子管线**：效果用数据描述（type/magnitude/duration/stack），战斗管线 pre-hit→calc→shield→post-hit 分阶段（MudForge 8 类效果、ryuis 4 段管线）。
5. **同时回合制 PVP + ELO/Glicko**：文字/回合制游戏的公平竞技主流。
6. **自动化平衡验证**：用批量模拟统计 TTK/资源周转/连招率替代主观调参（CSDN 三锚点法）。

## 4. PVP 战斗设计方案（候选 → 推荐）

### 4.1 三套候选方案

| 方案 | 核心 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| **A. 轻量切磋（无惩罚）** | 复用 `duel()`，纯切磋不掉血不掉钱，仅荣誉战绩 | 改动最小、零风险、快速上线 | 无激励，玩两把就腻 | 第一步试水 |
| **B. 竞技场 + ELO（推荐）** | 统一内核 + ELO 匹配(±400) + 同时回合制选招 + 段位/赛季奖励 | 公平、有长期目标、战术深度、行业验证 | 工作量中等，要设计选招交互与防 abuse | 正式 PVP |
| **C. 世界 PVP（掠夺升级）** | 现有「抢」加 ELO/保护/奖惩，开放野外 PK | 刺激、经济联动 | 易被滥用、平衡难、QQ 群场景骚扰风险高 | 谨慎，最后做 |

### 4.2 推荐：方案 B（竞技场 + ELO + 同时回合制），分三阶段

**统一内核重构（前置，所有方案共用）**
- 把 `fight` / `duel` 的回合循环抽成 `core.battle(a, b, *, mode)`：
  - 双方抽象为「战斗单位」（属性+四槽+fx 状态+资源），怪物与玩家都适配同一接口；
  - 行动选择策略可注入：`random`(现有PVE) / `scripted`(玩家PVP选招) / `ai`(怪物)；
  - `rng` 注入保持不变 → 确定性可复现。
- 战报沿用现有 log 契约（`who` 标记 + 特殊条目字段鲁棒），展示层零改或微改。

**阶段一：轻量切磋（方案 A，先上线验证）**
- 新口令：`切磋 @某人`（需双方同意）/ `切磋榜`。
- 复用 `duel()`，结果只更新荣誉战绩（新建 `pvp` 字段：wins/losses/streak），**不扣血不扣钱**。
-  acceptor 同意机制：发起→目标确认（40秒超时）→结算。
- 验收：e2e 双人对战、同意/拒绝/超时、战报双方可读、无经济副作用。

**阶段二：竞技场 ELO（方案 B 核心）**
- 新增 `pelo`（初始 1000，K=32/16 分级，范围 ±400，地板 600）+ 每日目标次数限制。
- 新手 72h 保护、战败 2h 保护（对齐行业反虐菜）。
- **同时回合制选招**：每回合双方各选 攻击/技能1/技能2/防御/道具(可选)，结算前互不可见 → 用现有 `on_regex` 收集玩家输入（QQ 群天然适合「报招」）。
- 段位（青铜→王者，隐藏 MMR + 可见段位双层）+ 赛季奖励（荣誉/称号/稀有异火碎片）。
- 反 abuse：API 层限流、异常胜率审计、拒绝重复刷同一目标。

**阶段三：平衡与深度增强（可选）**
- 属性克制（斗破世界观：异火属性相克，契合原著）；
- 战斗道具（服用丹药回血/解毒，激活背包）；
