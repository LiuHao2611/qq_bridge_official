# 斗破源码问答沙盒（agent 容器）

> 建立时间：2026-11-17 深夜 ~ 2026-11-18 凌晨
> 触发原因：用户原话 **「你直接搬一个完整的agent项目吧，运行在沙盒里，docker应该可以满足，这样无论我怎么问他都能找到我想要的东西，而且不会影响我的电脑文件风险」**

## 0. 一句话

群里问斗破的任何细节（数值、概率、分支、设计取舍），主进程把**用户原话**丢给一个跑在独立容器里的
代码分析 agent；它自己 grep 源码、按行号读实现、写 Python 代公式算数，返回**带「文件名:行号」出处**
的中文答案。容器只读挂载源码，写不进宿主。

## 1. 为什么上一版不行

上一版是自研白名单检索（`src/plugins/qq_bridge/tools/code_explain.py`，三段式 outline/body/where）。
它能做的是「把正确的代码片段捞出来给模型看」，天花板在三处：

| 它做不到 | 后果 |
|---|---|
| 不知道去哪儿找 | 只能看白名单里 44 个文件的固定集合，看不见 import 链 |
| 不会缩范围 | 不能 grep，长文件只能整段贴或截断 |
| 不会算数 | 问「第 37 层爆装备概率」，它只能把 `0.25 × 0.08` 的源码贴出来，模型得自己算 |

真 agent 恰恰补这三样：**自己决定看哪个文件**、**自己拼命令缩范围**、**自己写 Python 代数字**。

## 2. 架构

```
QQ 群消息
   │
   ▼
qq-bridge-official（主 bot 容器）
   │  LLM 判断这是"问斗破实现细节" → 调工具 doupo_code_ask(question)
   ▼
POST http://qq-doupo-agent:8765/ask   （compose 内部网络，不暴露宿主端口）
   │
   ▼
qq-doupo-agent（沙盒容器，openai-agents 底座）
   │  shell(grep/sed/head/python3) + read_file   ← 只读挂载 /repo
   │  多轮：查 → 读 → 算 → 再查
   ▼
{"answer": "...", "tool_calls": 7, "elapsed": 42.1}
   │
   ▼
主 bot 的模型拿到答案 → 用自己的话回给群友
```

**一个工具，不是三个。** 旧的 `doupo_code_explain`（topic→file→symbol 三步）已从工具总线摘掉：
两个同类工具并存时，模型会在「快但浅」和「慢但深」之间反复横跳，最后又退化成只给签名。
现在工具表里只有 `doupo_code_ask`（15 个工具，数量与之前一致）。

## 3. 底座选型：为什么是 openai-agents，不是 smolagents

第一版搬的是 HuggingFace `smolagents.ToolCallingAgent`（1.26.0）。在这条火山 Ark 兼容端点上
**多轮必然退化**。容器内 dump 的实证：

```
[dump] msgs=2  chars=4447  tool_calls=0 roles=[system, user]      tc='required'
[dump] msgs=6  chars=8046  tool_calls=0 roles=[...,assistant,user]
Error while parsing tool call from model output: The model output does not contain any JSON blob.
[dump] msgs=14 chars=15562 tool_calls=0 ... stop=None tc=None
Reached max steps.
```

根因不在模型、在库的消息扁平化：

```python
# smolagents/models.py
tool_role_conversions = {
    MessageRole.TOOL_CALL:     MessageRole.ASSISTANT,
    MessageRole.TOOL_RESPONSE: MessageRole.USER,     # ← tool 结果降级成 user 文本
}

# get_clean_message_list() 只拷 role/content —— assistant.tool_calls 整个字段被丢掉
```

于是每轮历史都被压回「文本 ReAct」：模型看不到自己上一轮的结构化调用，只看到一句
`Observation: ...`。第一轮能出 tool_calls，第二轮就退回纯文本吐 `Calling tools: [...]`，
解析失败 → 跑满步数 → 偶尔蒙对一次"成功"。

换成 **openai-agents**（OpenAI 官方 Agents SDK，0.24）后走标准协议
（`assistant.tool_calls` → `role="tool"` 回灌），同一道题一次通过：
**42s / 9 次工具调用**，答案连「第 37 层根本不是 BOSS 层」这个前提错误都纠了出来。

> 换模型/换端点时若又出现「工具调不通但短问题能答」，先怀疑这层消息格式，不要怀疑模型。

## 4. 沙盒边界（用户「不影响我的电脑文件」是硬要求）

| 手段 | 实际效果（容器内实测） |
|---|---|
| 源码 `:ro` 挂载，只挂 4 处 | `touch /repo/x` → `[Errno 30] Read-only file system` |
| 根文件系统 `read_only: true` + `/tmp` tmpfs | `touch /pwned` → 同上 |
| 非 root（uid 10001） | `id -u` = 10001 |
| `.env` **不在挂载列表** | 容器里 glob 不到任何 `.env` |
| `environment:` 只列 6 个变量（不用 `env_file`） | 环境里没有 QQ_/NAPCAT/TTS/TOKEN 类密钥 |
| 不挂 docker socket | `/var/run/docker.sock` 不存在 |
| `cap_drop: ALL` + `no-new-privileges` | 无提权面 |
| 不映射端口 | 只有同 compose 网络的 bridge 能访问 |
| `shell` 命令黑名单（第二道保险） | `rm -rf` / `mv` / `chmod` / `>` 重定向 / `curl` 一律返回「拒绝执行」 |

**证明脚本**（不是"看代码觉得安全"，是真在容器里试）：

```bash
docker exec -i qq-doupo-agent python - < tests/evidence/prove_agent_sandbox.py   # 17 条全 PASS
```

## 5. 接口与配置

```
GET  /health  → {"ok":true,"model":...,"max_turns":14,"max_tools":10,"timeout":150,"sdk":"openai-agents 0.24.0"}
POST /ask     → {"question": "..."}            # 用户原话，整句传
              → {"answer":"...", "steps":n, "tool_calls":n, "tools":[...], "elapsed":12.3}
              → 失败 500 {"error": "RateLimitError: ..."}   ← 绝不返回"看起来成功"的空答案
```

| 变量 | 位置 | 默认 | 说明 |
|---|---|---|---|
| `DOUPO_AGENT_URL` | 主 bot | `http://qq-doupo-agent:8765` | 服务地址 |
| `DOUPO_AGENT_TIMEOUT` | 主 bot | 160 | 单次问答总预算（同时作为工具的 per-tool timeout） |
| `AGENT_MAX_TURNS` | agent | 14 | SDK 步数上限；撞上会抛 `MaxTurnsExceeded`、**答案整个丢掉**，所以留足余量 |
| `AGENT_MAX_TOOLS` | agent | 10 | 工具预算（机械刹车）：第 11 次起直接返回「立刻停止检索、用已有材料作答」 |
| `AGENT_TIMEOUT` | agent | 150 | agent 侧总预算 |
| `AGENT_VERBOSE` | agent | 0 | =1 时每调一个工具打一行 |

## 7. 踩过的坑（每条都有真机证据，别再踩）

1. **`read_only: true` 时 docker 不会自动创建挂载目标目录** —— 挂载静默不生效，容器里 `/repo`
   是空壳，agent 跑 10 次工具全报 `[Errno 2] No such file or directory: '/repo'`，最后诚实回了
   「源码仓库不存在」。解法：Dockerfile 里 `mkdir -p` 出那 4 个空目录。
2. **每请求 `asyncio.run()` → 第二个请求必炸 `Event loop is closed`** —— `AsyncOpenAI` 的 httpx
   连接池绑定首次使用的事件循环。解法：一个常驻循环线程 + `run_coroutine_threadsafe`。
3. **Git Bash 下 `-v "$PWD:..."` 会把 `/d/AI/...` 传成 Linux 路径** → 挂出空卷。用 `$(pwd -W)`；
   同理 `docker exec ... python /tmp/x.py` 要加 `MSYS_NO_PATHCONV=1`。
4. **`MAX_TURNS` 撞顶 = 答案全丢**（SDK 抛异常，没有部分结果）。所以要有工具预算刹车，
   而不是靠调大 max_turns。
5. **提示词约束不住步数**：写「控制在 6 次以内」，模型照样查到 11~14 次（最长 141 秒）。
   必须在工具里硬拦。
6. **`openai` 客户端默认对 429 静默重试退避**，上层表现成"请求挂死 300 秒"。必须
   `max_retries=0` 让失败立刻显式化。
7. **tracing 默认会往 OpenAI 上传**：`set_tracing_disabled(True)` + `OPENAI_AGENTS_DISABLE_TRACING=1`，
   顺序不能反（要在任何 `Runner.run` 之前）。

## 8. 已知限制

* **延迟 40~90 秒**：实测 5 次调用 ≈ 43s，11 次调用 ≈ 93s。深度换来的，压不下去
  （压输出上限 / 加机械刹车已经从 67s → 43s、141s → 封顶 10 次）。
  若用户嫌久，可选方案：先回一句「去翻源码，稍等」再补答案（需要改主 bot 的两段式回复）。
* **额度**：agent 和主 bot 共用 `.env` 里的同一个 `AI_API_KEY`。火山 Ark 的
  「安全体验模式」是**按模型独立计**的免费额度，用完该模型就暂停服务
  （`SetLimitExceeded` / 429）。2026-11-18 凌晨实测：`glm-5-3-flash`、`glm-5-2`、
  `deepseek-v4-pro-ga`、`deepseek-v4-flash-ga` 全部到顶，`kimi-k3-1-pro` 未开通。
  → 需要去 Ark 控制台「模型开通」页关掉安全体验模式（转按量付费），或换 key。
