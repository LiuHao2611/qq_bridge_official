# 斗破「完整战斗回看 + 战斗评价」设计方案

> 记录时间：2026-11-17  
> 对应需求（用户原话）：  
> “目前战斗会省略掉中间的细节，这个是没问题的，我要求增加一个查看完整战斗的功能，可以查看最后一次战斗的完整过程，详细到每次使用了什么招式，包括普通攻击，消耗了多少血量，斗气，，触发了什么词条等等，最终输出文字会比较多，输出为卡片即可，然后同时输出一个按钮，战斗评价，这个评价，评语偶尔简短偶尔很长，但都有满满的嘲讽意味，你去做深度调研，爬取别人的评语过来用”

---

## 1. 结论先行

本轮新增两个口令，保持原有「战斗回包只给高光，不膨胀」的口径不变：

| 口令 | 作用 | 输出 |
|---|---|---|
| `战斗回看` | 查看**最后一次战斗**的完整逐条过程 | 图片卡片 + 同条消息按钮「战斗评价」 |
| `战斗评价` | 基于最后一场战斗的真实数据，生成一句/一段嘲讽评语 | 文本 |

关键设计：

1. **只新增一个统一落盘点**：`core.record_last_battle()`。
   - 普通遭遇、掠夺、无惩罚切磋、爬塔、周副本全部调用；
   - 数据写入玩家存档 `data` JSON 的 `last_battle` 字段；
   - SQLite 的 `players.data` 列无需改表结构。
2. **不破坏既有普通战斗回包**：`cmd_fight()` 继续只展示 `_battle_highlights(limit=1)`，中间细节仍折叠；完整过程只在玩家主动发 `战斗回看` 时出卡。
3. **战斗日志补字段而不是换结构**：现有 `log` 条目继续保留 `kind/dmg/crit/skill/notes`，额外补 `move/hp_before/hp_after/mp_before/mp_after/mp_cost/round/foe_hp_before/foe_hp_after`，保证旧字段消费方零改动。
4. **官方通道图片+按钮绝不分离**：新卡通过 `finish_card(..., "battle")` 发送，`CARD_ACTIONS["battle"] = ("战斗评价",)`；素材上传失败仍按既有 `image_only` 策略只发图片，不另发按钮条。
5. **评语库做原创改写，不整段搬运**：参考网络 community 吐槽句式，只嘲讽战斗表现，不做人身攻击；每条保留 `source` 字段记录灵感来源。

## 2. 现状调研

### 2.1 战斗内核

现有战斗统一走 `src/plugins/doupo/core.py`：

- `fight(p, mon, ...)`：单敌战斗；
- `encounter(p, ...)`：1~5 敌连续遭遇，逐个复用 `fight()`；
- `duel(p, vic, ...)`：掠夺/切磋共用双人模拟器；
- `tower_floor()` / `weekly_floor()`：克隆玩家状态调用 `fight()`，避免污染永久存档。

现有 `fight()` 返回：

```python
res = {
    "win": win, "rounds": shown_rounds, "log": dmg_log,
    "taken": taken, "mon": mon, "mon_hp_left": max(0, m_hp),
    "hero_aid": aid,
}
```

现有 log 条目示例：

```python
{"dmg": 328, "crit": True, "kind": "狂狮怒罡", "skill": True,
 "notes": ["破甲", "连击"], "heal_ratio": 0.0}
```

问题：

- 没有逐条 `round` / `mp_cost` / `mp_after` / `hp_after` / `foe_hp_after`；
- `kind` 对技能就是招式名，普攻叫 `普攻`，但没有显式的 `move` 字段；
- 没有统一的「战斗结束」落盘钩子；
- 爬塔/周副本用的是玩家深副本，若在 `fight()` 内直接写 `p`，不会落到真实存档。

### 2.2 展示层

`commands.cmd_fight()` 当前只做：

```python
all_log = [it for x in detail for it in x.get("log", []) if isinstance(it, dict)]
hi, folded = _battle_highlights(all_log, limit=1)
```

`_battle_line()` 已实现属性归因：

```python
via = "力量·斗气" if it.get("skill") else "力量·武器"
if it.get("crit"):
    via += "·暴击(敏捷)"
```

这些归因文案继续复用，完整卡不另造第二套口径。

### 2.3 存档层

`store.py` 结构：

```sql
CREATE TABLE IF NOT EXISTS players (
    qq TEXT PRIMARY KEY,
    group_id TEXT NOT NULL DEFAULT '',
    lv INTEGER NOT NULL DEFAULT 1,
    exp INTEGER NOT NULL DEFAULT 0,
    gold INTEGER NOT NULL DEFAULT 0,
    updated_at REAL NOT NULL DEFAULT 0,
    data TEXT NOT NULL
);
```

玩家完整 dict 存 `data` 列，新增 `last_battle` 只需写 JSON，不改 schema。路径仍只由 `DATA_PATH` 推导，遵守「路径单源」铁律。

### 2.4 卡片层

`doupo_help.py` 是现有最适合复用的蓝本：

- 单列分组；
- `_wrap()` 用真实字体宽度折行；
- `_layout()` 测高与绘制共用；
- `boxes` 收集包围盒供自检；
- 无 emoji，字体安全。

新卡 `doupo_battle.py` 复用这套骨架，图标换 `sword`，标题改「战斗回看」。

### 2.5 按钮/菜单守门

既有硬约束：

- `MENU_GROUPS` 必须保持纯字面量，测试用 `ast.literal_eval` 读；
- canonical 口令取每条口令首词；
- matcher 数必须等于 `menu_total()`；
- `CARD_ACTIONS` 每张卡按钮 1~5 个，组合不能与其他卡完全相同；
- 按钮口令必须在 `button_dispatch._PLAN` 有真实函数；
- 新卡 `card_key` 必须在 `CARD_ACTIONS` 中登记。

## 3. 嘲讽评语调研与合规口径

### 3.1 参考来源（检索于 2026-11-17）

| 来源 | 检索到的句式/方向 | 处理方式 |
|---|---|---|
| 微信公众号《20 条攻击力超强的王者怼人语录》 | “你这输出像签了保密协议，全程不透露伤害”“我以为你在骗技能，后来发现你是在骗自己”“你别说话了，你的战绩已经替你发言了” | 取「保密协议/战绩替你发言」的比喻骨架，改写为斗破语境 |
| 什么梗百科 / 新词百科《一顿操作猛如虎》 | “一顿操作猛如虎，一看战绩零杠五”“一看原地杵” | 取反差节奏，改写为「一顿操作猛如虎，一看伤害二百五」等 |
| NGA 玩家社区《鸟德改了个寂寞！》 | “一顿操作猛如虎，一看伤害还是二百五” | 取「操作与结果反差」方向，不复制原文段落 |
| 王者荣耀/和平精英社区常见吐槽 | “打了个寂寞”“输出像天气预报”“伤害还没我打字快” | 只作灵感，入库文本全部二次原创 |

> 合规口径：不直接搬运整段文章；不做人身攻击；不出现真实玩家昵称、地域、性别、职业等攻击维度；只嘲讽战斗数据本身（伤害、血量、斗气、回合数、暴击、闪避、被控、机缘）。

### 3.2 评语库结构

新增 `battle_comments.py`：

```python
SHORT = (
    {"text": "这伤害挺保密的，敌人生死全靠猜。", "tag": "low_dmg", "source": "..."},
    ...
)
LONG = (
    {"text": "一顿操作猛如虎，一看伤害二百五。斗气烧得挺热闹， blood条却像没收到通知……", "tag": "low_dmg", "source": "..."},
    ...
)
```

选择规则：

1. 根据最后一场战斗提取标签：`win / lose / low_dmg / high_dmg / low_mp / high_taken / many_rounds / crit / miss / aid / dot / reflect / control`；
2. 用 `openid + ts + log_len` 作种子，保证同一场战斗每次点「战斗评价」结果稳定；
3. 长短比例约 2:1（多数短、偶尔长），但可通过种子自然波动；
4. 标签优先命中，未命中则用胜负通用池；
5. 输出纯文本，不新增卡模板。

## 4. 数据设计

### 4.1 `last_battle` 落盘结构

```python
p["last_battle"] = {
    "version": 1,
    "ts": 1763410000.0,
    "kind": "遭遇" | "切磋" | "掠夺" | "爬塔" | "周副本",
    "win": True,
    "rounds": 12,
    "opponent": "摩云藤等3名" | "道友ABCD",
    "player": {
        "name": "萧炎", "lv": 30, "power": 12345,
        "hp": 820, "hp_max": 1000, "mp": 40, "mp_max": 600,
    },
    "summary": {
        "taken": 180, "exp": 320, "gold": 450,
        "drops": [["炎星石", 1]],
        "enemy_count": 3, "enemies": ["摩云藤", "铁甲蜥", "猎豹"],
    },
    "log": [
        {
            "round": 1, "foe": "摩云藤", "move": "狂狮怒罡",
            "dmg": 328, "crit": True, "skill": True,
            "notes": ["破甲", "连击"],
            "hp_before": 900, "hp_after": 900,
            "mp_before": 600, "mp_after": 560, "mp_cost": 40,
            "foe_hp_before": 1200, "foe_hp_after": 872,
        },
        ...
    ],
}
```

### 4.2 完整卡行格式

每条 log 固定两行（实测宽度后用 `wrap_cjk` 折行）：

```text
01｜第1敌·回合2｜狂狮怒罡 328（力量·斗气·暴击敏捷）
   气血 900→900　斗气 600→560(-40)　敌血 1200→872　词条 破甲、连击
```

兽击/反伤/闪避/持续伤害/被控：

```text
02｜第1敌·回合2｜兽击 86（防御减伤）
   气血 900→814　斗气 560→560　敌血 872→872
```

贵人相助：

```text
01｜第1敌·回合1｜贵人相助 9999（机缘）
   ——无名斗皇一招制敌，气血 900→900，斗气 600→600
```

## 6. 验收计划

1. **单元测试**
   - `core.fight()` 的 log 含普攻/技能名、hp/mp 轨迹、词条；
   - `record_last_battle()` 写入 JSON 可序列化；
   - 五个战斗入口都写入 `last_battle`；
   - `cmd_battle_review()` 无战斗时返回友好提示；有战斗时返回完整文本兜底；
   - 评语库短/长均存在、标签命中、同场稳定；
   - 卡模板 `build(..., boxes=...)` 无越界/重叠。
2. **反例注入（prove-it）**

   - 把按钮口令改成编造口令 → 按钮守门必须红；
   - 把评语改成空 → 评价测试必须红。
3. **全量回归**
   - `tests/test_doupo_buttons.py`；
   - `src/plugins/doupo/test_commands.py`；
   - `src/plugins/doupo/test_menu_full.py`；
   - `src/plugins/doupo/test_e2e.py`；

## 7. 风险与边界

* **图片高度**：极端 5 敌 × 15 回合会产生约 150 条 log，卡片可能很高；本轮按「完整优先」不截断，测试只守常规场景高度，极端场景靠单列长图承载。
* **存档体积**：`last_battle` 单场通常几十 KB，SQLite JSON 列可承受；不存历史多场，只保留最后一场。
* **按钮不分离**：若素材上传失败，按既有 `image_only` 策略只发图片；用户曾明确「不许分开发按钮条」。
* **不降级出图**：`战斗回看` 原有能力就是出图，渲染失败必须有纯文本兜底但不得静默；这与「原本能输出图片的口令不要降级为纯文字」不冲突——降级只在渲染异常时兜底，正常路径必出图。
* **评语边界**：嘲讽只针对战斗表现，避免人身攻击；不做真实玩家画像。
