# 斗破卡片渲染性能 · 深度调研与优化方案

> 版本：v1.2 ｜ 日期：2026-11-23 ｜ 状态：**P0-1 + P0-2 + P1 全部实施并上线（17:25），实测见 §12/§13**
> 触发：用户「发送卡片比较慢，不知道是环境问题还是程序问题」→「深度调研权威大佬怎么做，认真验证一遍，再给优化建议」
> 证据原则：本文所有耗时数字均为真跑实测（标注测试机），无估算、无编造；未能验证的一律列在 §11。

## 0. 一页速览

**结论：不是环境退化，也不是代码 bug。是「主题重做引入的静态装饰 + PNG 编码参数」两项固定成本，叠加手机单核算力。**

三个可直接落地的改动，全部**不改变任何视觉呈现**：

| 编号 | 改动 | 手机实测收益（人物卡 720×810） | 风险 |
|---|---|---:|---|
| **P0-1** | `canvas.to_bytes()` 的 PNG 编码 `optimize=True` → `compress_level=6` | **−514ms（41%）**，体积 +4.4% | 极低（单行） |
| **P0-2** | `doupo_ui.card_shell` 外壳底图按主题缓存 | **再 −527ms**，12 张斗破卡全部受益 | 中低（需内存 LRU） |
| **P0-1+2** | 合计 | **1262ms → 221ms（−82%）** | — |
| P1 | `_build_merged_card_segment` 多图上传并行化 | 多图场景每图省 ~1 次 RTT | 低 |
| P2 | 素材库 92 顶格治理 | 消除 LRU 抖动 | 可选 |

**关键因果（新发现）**：11-22 卡片主题改成游戏风（云纹/辉光/暗角）后，人物卡渲染从 **466ms 涨到 1295ms（2.8×）**。变慢的起点就是主题重做，不是环境变化。

**同时撤回上一轮的一条错误建议**：「缓存键精简（把 exp/gold 从 key 剥离）」会导致卡面显示旧数值，属于错误，见 §5.5。

### 1.1 用户感知

群内触发斗破卡片命令后，图片到达明显有延迟（体感数秒）。

### 1.2 判定口径

把端到端拆成四段，分别归属「程序可控 / 环境不可控」：

| 段 | 归属 | 线上 p50 | 可否用代码压缩 |
|---|---|---:|---|
| 渲染（build + PNG 编码） | **程序** | 650ms（全模板中位）<br>人物卡 1295ms | ✅ 可以 |

### 2.3 缓存设计（Milan Jovanović 内容寻址缓存 / CDN shell-fragment）

| 权威原则 | 本项目对照 |
|---|---|
| 缓存键 = 「影响输出的**最小充分输入集**」，过宽导致 cardinality explosion | `make_key` 已纳入字体版本/代码签名/主题签名（正确），但把全量 `params` 纳入 → 动态卡必然 miss |
| **静态壳（shell）长缓存 + 动态片段（fragment）单独渲染** | 项目**未做**，整图每次重绘 → **最大改进空间** |
| 内容寻址：把代码/配置/字体当显式输入 | 项目已做（`_code_sig()`、`_font_ver()`） |
| 不要把「有新鲜度语义」的数据做内容键（价格、库存、徽标数） | 玩家 exp/gold/hp 正是此类 → **不能剥离出 key**（见 §5.5） |

## 3. 根因分析（4 条，均有实测支撑）

### 3.1 根因一：PNG 编码参数选错，手机上是最大单项成本

`pic/canvas.py:532`：

```python
Image.alpha_composite(base, self.img).convert("RGB").save(buf, format=fmt, optimize=True)
```

`optimize=True` 在 PNG 上会尝试多种 filter + 最高 zlib 压缩，是纯 CPU 单线程。**骁龙 835 的 zlib 性能是短板**，所以手机上的相对成本远高于电脑。

真机实测（720×810 人物卡，各 5 次中位）：

| 参数 | 耗时 | 体积 | 相对现状 |
|---|---:|---:|---:|
| `optimize=True`（现状） | **614.3ms** | 169.5KB | 基准 |
| `optimize=False` | 43.4ms | 177.0KB | −571ms，+7.5KB |
| **`compress_level=6`** | **100.6ms** | 177.0KB | **−514ms，+4.4%** |
| `compress_level=3` | 31.6ms | 193.8KB | −583ms，+14% |
| `compress_level=1` | 21.5ms | 265.8KB | −593ms，+57% |

> 电脑端同样测试：162.8ms → 42.1ms（`compress_level=6`）。
> **选择 `compress_level=6`**：省 84% 编码时间，体积只增 4.4%（7.5KB，对上传耗时影响 <10ms 量级），是无损视觉的最优平衡点。

#### 无损性硬验证（已实测）

同一张 720×810 画布，分别用两组参数编码后逐字节比对：

```
尺寸   opt=(720, 810)   c6=(720, 810)
模式   opt=RGB          c6=RGB
体积   opt=173287        c6=180866   (+4.4%)
逐像素字节差异数 = 0
像素级完全一致 = True
```

→ **PNG 是无损格式，压缩级别只影响体积与耗时，不改变任何像素。** 这是 P0-1 零视觉风险的硬证据。

### 3.2 根因二：游戏风主题的静态装饰成本被重复支付（最大项）

`pic/templates/doupo_ui.py` 有 **8 处 GaussianBlur**，全部服务于静态装饰：

| 位置 | 用途 | 半径 |
|---|---|---:|
| `card_shell` | 暗角 | **40** |
| `card_shell` → `glow` | 顶部天光 | 60 |
| `title_plaque` | 牌匾外辉光 ×2 | 9 / 3 |
| `cloud_band`/`scale_band` | 云纹/龙鳞 | 大半径 |
| `_grad_on` | 标题发光 | 7 |

这些**只依赖 (主题配色, 宽, 高, 标题)**，与玩家数据无关，但每次渲染都重算。

真机实测（720×810）：

```
外壳 card_shell（含全部模糊）  p50 = 527.5ms
整卡 build（不含编码）        p50 = 648.0ms
  └ 内容层（文字/头像/网格/条） p50 = 120.5ms  (18.6%)
```

**即 81% 的绘制时间花在只有 3 个变量的静态外壳上。**

#### 时间序列证据：变慢起点就是主题重做

`doupo` 模板按小时 p50（同一台手机、同一份代码）：

| 时间 | n | p50 | 说明 |
|---|---:|---:|---|
| 11-21 20:00 | 3 | 467.1ms | 旧主题 |
| 11-22 07:00 ~ 19:00 | 8 | 438~554ms | 旧主题稳定 |
| 11-22 22:00 | 5 | 464.3ms（max 1230.9） | **主题重做上线，出现首批 1.2s** |
| **11-23 14:00** | 2 | **1295.2ms** | 新游戏风主题，**较旧主题慢 2.8×** |

> 独立复现：用当前代码 + 新主题，手机连测 10 次 `doupo` 渲染为 1225~1267ms（p50=1236.7），与线上 1295ms 吻合。
> 结论：**「卡片变慢」的时间点 = 用户 11-22 重做卡片主题的时间点**，与服务器迁移、网络、负载无关。

### 3.3 根因三：整图重绘，没有 shell/fragment 分离

`doupo.py::build` 每次从头画：外壳 → 头像 → 文字 → 进度条 → 六维网格 → 血条 → 底栏。而其中只有「数值」在变，版式与装饰完全固定。

**版式高度固定**（`_measure(data)` 不依赖 data），这是分层的前提条件，天然成立。

### 3.4 根因四（澄清，非缺陷）：100% cache miss 的真实原因

上一轮报告说「动态卡天然难命中」，本轮做了更严格的验证，需要修正表述：

- **探针 `probe_png_determinism`**：同一 params 连渲 6 次，`png_md5_unique=1/6`、`key_unique=1/6` → 编码**完全确定**，排除「非确定编码」。
- **探针 `probe_data_volatility`**：同一玩家连续两次 `build_data`，**0/26 字段变化**；改了 `exp/gold/hp` 后，**恰好只有这 3 个字段变**。
- 因此 `cache=miss` 的真因是：**日志样本内不存在「同玩家 + 同状态 + 同卡」的重复请求**（不同玩家、不同卡、或操作后状态已变），而不是缓存机制失效。

**这一点很重要**：它说明「提高磁盘缓存命中率」的收益有限（玩家操作后必然重渲染），而**降低单次渲染成本（P0-1/P0-2）对每一次请求都有效**，是更稳的收益来源。

## 5. 优化方案

### 5.1 P0-1：PNG 编码参数（单行，零视觉变化）

**落地点**：`src/plugins/qq_bridge/pic/canvas.py:532`（`Canvas.to_bytes`）

```python
# 现状
Image.alpha_composite(base, self.img).convert("RGB").save(buf, format=fmt, optimize=True)

# 建议
Image.alpha_composite(base, self.img).convert("RGB").save(
    buf, format=fmt, compress_level=_PNG_COMPRESS_LEVEL)
```

`_PNG_COMPRESS_LEVEL = 6` 定义在模块顶部并注释理由。`save()`（落盘路径，537 行）同步处理。

**注意**：
- 只对 `fmt == "PNG"` 生效；其它格式走原参数，避免 JPEG 不认 `compress_level`。
- `optimize` 与 `compress_level` 不同时给（Pillow 会以 optimize 覆盖）。
- 体积 +4.4% 会使素材上传多 7.5KB，实测对上传耗时影响在 10ms 量级，可忽略。

**收益**：手机端人物卡 −514ms（41%）、menu −1246ms（44%）、battle −664ms（35%）。

### 5.2 P0-2：外壳底图缓存（12 张卡统一受益）

**为什么一处改动全卡受益**：全部 14 个斗破模板都通过 `UI.card_shell(c, p, title, ...)` 画外壳：

```
doupo.py:333        doupo_menu.py:296      doupo_battle.py:933
（其余 doupo_craft / faction / help / list / puppet / recipes / roster / ruin / skills 同源）
```

**输入稳定性**：`card_shell(c, g, title, *, top, width)` 的输入只有
- `W, H`：画布尺寸（固定）
- `g`：主题配色字典（换主题才变）
- `title`：标题文案（固定，如「斗破大陆」「战斗回看」）
- `top` / `width`：固定

**与玩家数据完全无关** → 缓存键 `(主题签名, W, H, title, top, width)`，命中率接近 100%（除首次与换主题）。

**实现骨架**（`doupo_ui.py`）：

```python
from collections import OrderedDict
import hashlib, json

_SHELL_CACHE: "OrderedDict[str, tuple]" = OrderedDict()
_SHELL_MAX = 16          # 720×810 RGBA ≈ 2.33MB/条 → 上限约 37MB

def _shell_key(g: dict, W: int, H: int, title: str, top: int, width) -> str:
    raw = json.dumps([g, W, H, title, int(top), int(width or 0)],
                     sort_keys=True, ensure_ascii=False)
    return hashlib.sha1(raw.encode("utf-8")).hexdigest()[:16]

def card_shell(c, g, title, *, top=0, width=None):
    img = img_of(c)
    W, H = img.size
    key = _shell_key(g, W, H, title, top, width)
    hit = _SHELL_CACHE.get(key)
    if hit is not None:
        _SHELL_CACHE.move_to_end(key)
        shell_img, content_y = hit
        img.paste(shell_img, (0, 0))
        return content_y
    # ... 原绘制逻辑不动 ...
    content_y = y2 + 20
    _SHELL_CACHE[key] = (img.copy(), content_y)
    if len(_SHELL_CACHE) > _SHELL_MAX:
        _SHELL_CACHE.popitem(last=False)
    return content_y
```

**关键约束**：
- 缓存的是**整幅**外壳（含底色），命中时用 `paste` 覆盖，不能用 `alpha_composite`（会重影）。
- `content_y` 必须一起缓存（它由 `top`/`width` 推出，但缓存更省事且防漂移）。
- 主题编辑器改色 → `g` 变 → key 变 → 自动失效，无需手动清缓存（内容寻址的红利）。
- 首次请求仍需付全额（527ms），从第二次起命中。

**收益**：手机端再省 527ms；与 P0-1 叠加后 **1262ms → 221ms（−82%）**。

**为什么不做「动态层叠加」的更激进方案**：`probe_layered_render` 显示叠加层只需约 3ms、相对整图重绘约 147~168×（多次测量波动），但它要求把每个动态字段拆成独立图层并精确对齐，会改动 12 张卡的版式代码，回归风险高。P0-2 只碰一个函数，收益已达 82%，**先做低风险版本**（符合「不做无必要的大改」）。

### 5.3 P1：多图上传并行化

**落地点**：`src/plugins/qq_bridge/channel/official.py:156-159`

```python
# 现状：串行
for i, data in enumerate(image_datas):
    mat = await ensure_material(bot, data, file_name="card_%d.png" % i)
    parts.append(markdown_image(mat["url"], mat["width"], mat["height"], alt=img_alt))

# 建议：并发（保持 parts 顺序）
mats = await asyncio.gather(*[
    ensure_material(bot, data, file_name="card_%d.png" % i)
    for i, data in enumerate(image_datas)
])
parts = [markdown_image(m["url"], m["width"], m["height"], alt=img_alt) for m in mats]
```

**注意**：
- `ensure_material` 内部只在配额错误时持 `_quota_lock`，正常路径无锁，`gather` 安全。
- 失败语义保持：任一失败 `gather` 抛 `MaterialUploadError`，上层仍降级两条发送。
- 收益只在多图场景（分页卡/合并图）体现；单图无变化。

### 5.4 P2：素材库 92 顶格治理（可选）

**现状**：`media_assets.json` 92 条顶格，`(720,724)` 独占 34 条，`cached_store=92` 长期打满 → 每次新图都触发 LRU 删除。

**建议**（按需，不急）：
1. 给 `MaterialStore` 增加「按尺寸/卡类型分组配额」，人物卡保留最近 N 张（如 12），防止单一卡类型挤占全部配额。
2. 日志加 `material_lru_evicted` 计数，便于观察淘汰频率。
3. **不要**通过降低 `MAX_MATERIALS` 来缓解——那会让更多图重传，适得其反。

> 注：P0-1/P0-2 不改变最终 PNG 字节，因此**不会减少素材上传次数**。此项与 P0 独立。

### 5.5 撤回：上一轮的「缓存键精简」建议

上一轮建议「把 exp/hp/gold 从缓存 key 剥离或分段」，**本轮验证后撤回**：

- `probe_data_volatility` 证明：玩家操作后恰好只有 `exp/gold/hp` 变。
- 这三个字段**正是卡面上显示的数值**。把它们从 key 剥离 → 命中旧图 → **玩家看到过期数值**，属于错误行为（违反「禁止兜底/禁止假数据」纪律）。
- 权威原则同样反对：内容寻址缓存要求 key 覆盖「所有影响输出的输入」，`over-include` 只损失一次重算，`under-include` 会返回错误内容。

**替代做法**：不追求「提高命中率」，而是「降低每次未命中的成本」——即 P0-1 + P0-2。
