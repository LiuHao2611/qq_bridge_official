## 1. 这套环境到底是什么

### 1.1 它不是什么（先说清楚，避免误会）

| 不是 | 说明 |
|---|---|
| 不是 Android | 没有 Android 框架、没有 APK、没有「后台被杀」。这是裸机 Linux 直接跑在硬件上 |
| 不是 Termux / proot | 不是「Android 里套个 Linux 壳」，是内核直接引导起来的 Alpine |
| 不是 Docker | `docker ps` 是空的，**这台机器上没有容器**。所有服务都是 OpenRC 守护进程 |
| 不是虚拟机 | 没有宿主；手机就是服务器 |

### 1.2 它是怎么装起来的（结构，一句话能讲清）

```
eMMC
├─ sde40  boot 分区      → boot.img（内核 6.0.0 + initramfs + 定制 DTB）
├─ sde43  system 分区    → 一个 5G 的 loop 镜像文件
│                           ├─ loop0p1  221M  ext2  → /boot
│                           └─ loop0p2  4.6G  ext4  → /         ← 系统盘
└─ sda17  userdata 120G  → 完全没动（原 Android 数据还在，随时可刷回去）
```

验证命令（在手机上）：

```bash
losetup -a            # /dev/loop0: ... (/dev/sde43)
df -h / /boot         # loop0p2 挂 /，loop0p1 挂 /boot
```

### 1.3 能力边界（写清楚，省得以后白折腾）

| 能做 | 不能做 / 不该做 |
|---|---|
| 跑 bot、跑源码问答 agent、跑日志面板、SSH 维护 | 跑 ComfyUI 生图（显存/算力不够，且模型不在本机） |
| 24 小时常驻，断电自动恢复 | 当 NAS / 大流量下载机（WiFi 芯片有已知缺陷，见 §6.4） |
| 同时服务几十个群消息 | 编译大型项目（4.6G 系统盘 + 无 swap，会 OOM） |

**已知不可用项**（不是配置错，是物理限制）：`.env` 里 `MANJU_API_BASE=127.0.0.1:7788`、`TASK_MONITOR_BASE=127.0.0.1:8099` 指向的是**电脑上的主项目**，手机上没有，所以「生图 / 任务中心」这两个功能在手机上不可用。bot 其余功能正常。

## 2. 怎么登录 SSH（一步一步）

### 通道 A：局域网 WiFi（日常就用这个）

**前提**：电脑和手机连同一个路由器（手机固定 `192.168.0.50`）。

**第 1 步 · 确认手机在线**

在电脑上（PowerShell 或 Git Bash 都行）：

```bash
ping 192.168.0.50
```

期望：`来自 192.168.0.50 的回复: 字节=32 时间=10ms`（10~30ms 正常；>200ms 说明 WiFi 在抖，见 §6.4）。

不通就别急着折腾，先按 §7.4「SSH 连不上 / 网络断了」处理。

**第 2 步 · 登录**

```bash
ssh pmos@192.168.0.50
```

- **已配免密**（电脑的 `~/.ssh/id_ed25519` 在手机 `authorized_keys` 里），正常是**直接进**。
- 若提示要密码：`123456`。
- 首次连接会问 `Are you sure you want to continue connecting?` → 输 `yes`。

期望看到（默认 shell 是 busybox `ash`，提示符只有「当前目录 + 用户符号」，不是 bash 那种 `user@host`）：

```
~
$
```

`/etc/profile.d/color_prompt.sh.disabled` 存在但被禁用，所以没有颜色提示符，这是正常的，别去「修」它。

**第 3 步 · 拿到管理员权限**

看日志不需要 root（`pmos` 在 `wheel` 组，能读 `/var/log/messages`）；**管服务、改配置、动数据需要**：

```bash
sudo -i          # 输一次密码 123456，之后一直是 root（提示符变成 # ）
# 或者单条：sudo rc-service qq-bridge restart
```

`pmos` 在 `wheel` 组里，`sudo` 是 `(ALL) ALL`，没有限制。

**第 4 步 · 退出**

```bash
exit
```

#### 通道 A 的常见报错对照表

| 现象 | 判据 | 处理 |
|---|---|---|
| `Connection timed out` | `ping 192.168.0.50` 也不通 | WiFi 掉了 → 走通道 B，或等看门狗自愈（≤1 分钟），见 §7.4 |
| `Connection refused` | ping 通但 22 端口拒 | sshd 没起 → 通道 B 进去 `sudo rc-service sshd start` |
| `Permission denied (publickey,password)` | 密钥不匹配 | 用密码登录；或重新 `ssh-copy-id` |
| 连上就断 / 卡在 `Last login` | 内存或负载爆了 | 通道 B 进去 `free -m`、`uptime` |

### 通道 B：USB 数据线（救命通道，务必会）

WiFi 改错了连不上、sshd 挂了、要重装……都靠这条。**它不依赖 WiFi**。

**第 1 步 · 接线**

手机用**数据线**（不是纯充电线）接到电脑的 **USB 2.0 口**（主板后置优先，别用前置面板/集线器）。

**第 2 步 · 确认电脑识别到设备**

Windows「设备管理器 → 网络适配器」里应出现 **「远程 NDIS 兼容设备」**（Remote NDIS based Internet Sharing Device）。

> 若显示「未知 USB 设备（设备描述符请求失败）」：拔下来换一个 USB2.0 口重插；还不行就重启手机（长按电源 15 秒）。这条实践过两次，换口 + 重启必定恢复。

**第 3 步 · 给电脑这块网卡配 IP**

手机固定是 `172.16.42.1/16`，电脑要在同一网段：

1. `Win+R` → `ncpa.cpl` → 右键「远程 NDIS 兼容设备」→ 属性
2. 双击「Internet 协议版本 4 (TCP/IPv4)」
3. 选「使用下面的 IP 地址」：
   - IP：`172.16.42.2`
   - 子网掩码：`255.255.255.0`（或 `255.255.0.0`）
   - 网关、DNS 留空
4. 确定

**第 4 步 · 登录**

```bash
ssh pmos@172.16.42.1
```

**第 5 步 · 修完记得改回来**

WiFi 修好后，把那块网卡改回「自动获得 IP 地址」，否则可能影响电脑上网。

### 手机侧关键事实（排查时用得上）

| 项 | 值 | 验证 |
|---|---|---|
| 用户 | `pmos`（uid 10000，在 wheel 组） | `id` |
| 密码 | `123456` | — |
| WiFi 地址 | `192.168.0.50/24`，静态，网关 `192.168.0.1` | `ip -4 addr show wlan0` |
| WiFi MAC | 固定 `02:53:41:47:49:54` | `ip link show wlan0` |

## 3. 怎么启动系统（开机关机，一步一步）

### 3.1 开机

**只有一个动作：长按电源键，等屏幕亮起。**

没有「先起 A 再起 B」，因为全部是开机自启。上电后发生的事（**下列时间为实测约数**，
冷启动到 SSH 可连大约 40~60 秒；WiFi 本身握手快慢会浮动）：

| 时间 | 发生什么 | 出问题会怎样 |
|---|---|---|
| 0s | bootloader 引导 `sde40` 上的 `boot.img` | 黑屏/振动循环 = boot 分区坏了（见 §8） |
| 1~5s | 内核 6.0.0 起，挂载 loop0（rootfs）、启动 init | 卡在开机画面 = 镜像损坏 |
| 5~10s | udev 枚举硬件；`ath10k_snoc` probe、下载 WCN3990 固件 | `wlan0` 不出现 = WiFi 固件/驱动问题 |
| 10~40s | NetworkManager 用静态配置连 `FourSeasons_Plus_XA` | 连不上 → 看门狗（开机先睡 90 秒才上岗）兜底 |
| ~40s | `/etc/local.d/50-wifi.start` 跑：等 wlan0、`radio on`、最多 3 次 `connection up`，然后 **ntpd 校时** | 不校时 → 时间回到 1970 → 所有 HTTPS 全红 |
| 45s+ | OpenRC 按依赖拉起各服务（见下） | 某个服务 failed → 面板里一眼可见 |

服务依赖关系（谁等谁）：

```
net / NetworkManager
   ├── sshd
   ├── nftables
   ├── wifi-watchdogd
   └── qq-bridge           ← 会先等默认路由出现（最多 120s）
          └── qq-doupo-agent   ← after qq-bridge
   └── logview
```

### 3.2 开机后自检（8 条，照抄即可）

```bash
# 1) 网络与地址
ip -4 addr show wlan0 | grep inet          # 期望 192.168.0.50/24
ip route | grep default                    # 期望 default via 192.168.0.1 dev wlan0

# 2) 外网与延迟
ping -c 3 192.168.0.1                      # 期望 0% 丢包

# 3) 六个关键服务（rc-status 不需要 root，别加 sudo —— 加了反而会因为
#    没有 tty 拿不到密码而静默失败，看起来像「一个服务都没起」）
rc-status default | grep -E "qq-bridge|qq-doupo-agent|logview|wifi-watchdogd|sshd|nftables"
                                           # 期望全部 [ started ]

# 4) bot 是否连上 QQ（只认 "Bot <uin> connected"，别用单词 RESUMED —— 它会命中
#    official_event_arrived name=EventType.RESUMED 这种无关行，造成假阳性）
grep -E "Bot [0-9]+ connected" /home/pmos/qq_bridge/logs/service.log | tail -1
                                           # 期望 "QQ | Bot 1906371548 connected"

# 5) 源码问答 agent（手机没有 curl，用 wget）
wget -qO- http://127.0.0.1:8765/health    # 期望 {"ok": true, ...}

# 6) 日志面板
wget -qO- http://127.0.0.1:8091/health    # 期望 {"ok":true}

# 7) 内存与温度
free -m | head -2                          # 期望 used < 1000M
cat /sys/class/thermal/thermal_zone2/temp  # 期望 < 45000（=45℃，除以 1000）

# 8) 内核有没有 WiFi 报错（关键）
dmesg | grep -c "amsu\|msa info req rejected"    # 理想 0；非 0 见下面说明
dmesg | grep -c "successfully recovered"          # 截至目前自愈过几次（本次开机 5 次属正常）
```

> 第 8 条最重要：**补丁后（2026-11-21 23:10 起）`failed to extract amsdu: -11` 应为 0**——如果新出现，说明 ath10k 模块补丁掉了/被覆盖，先查 `md5sum /lib/modules/6.0.0/.../ath10k_core.ko.xz` 是否仍为 `913e7eb3c007b9fd613a2dfa75f3eba0`；历史上（补丁前）它表示 RX 停摆过。出现 `msa info req rejected: 90` 说明**有人 rebind 了驱动**，那是把机器玩死的操作，见 §8。开机残留的历史计数（本次验收基线 amsdu=4/recovered=6）是补丁加载前的旧记录，看**增量**而非绝对值。

### 3.3 关机 / 重启

```bash
sudo sync && sudo poweroff     # 关机（长期不用才关）
sudo sync && sudo reboot       # 重启（改配置后用）
```

**不要**长按电源键硬关（等于拔电，SQLite 可能留半写状态）。真要硬关前先 `sudo sync`。

重启后 bot 约 40~60 秒自动恢复，不需要人工干预。**不需要任何「手动拉起」步骤**。

### 3.4 开不了机怎么办（先别慌）

| 现象 | 含义 | 处理 |
|---|---|---|
| 长按无反应 | 电池空了 | 插电 10 分钟再试 |
| 一直黑屏无振动 | bootloader 未执行 | 插电脑看是否有 USB 设备枚举（`fastboot devices`） |
| 振动一下就停、循环 | 内核 panic | 插 USB 走通道 B 看 `pstore`（见 §7.7） |
| 开机但 SSH 连不上 | 网络没起来（更常见） | 走 USB 通道 B，读 `dmesg`/`/var/log/messages` |

**刷机回 Android 的退路仍然完整**：`userdata`（sda17）从未写过，TWRP 与官方包都在 `D:/AI/tools/android/`，按 `D:/AI/tools/android/PRE_FLASH_BACKUP_2026-11-21.md` 可回滚。

**查看/修改开机自启**

```bash
sudo rc-update show default            # 看哪些在 default runlevel
sudo rc-update add <服务> default      # 加自启
sudo rc-update del <服务> default      # 取消自启（保留服务本体，可随时 start）
```

**入口清单（每个 `/etc/init.d/<名字>` 的必填项）**

这台机器上所有「前台常驻进程」的 initd 都必须有这两行，否则会报
`start-stop-daemon: --stdout and --stderr are only relevant with --background` 然后直接 Failed：

```sh
pidfile="/run/${RC_SVCNAME}.pid"
command_background="yes"
```

## 5. 部署与更新代码（怎么把改动弄上手机）

> 手机是**运行端**，不是开发端。代码的源始终在电脑 `D:/AI/manju_agent/qq_bridge_official`。
> 手机上**没有 git 仓库、不联网拉代码**，全靠从电脑推。

### 5.1 先选对传输通道（这条踩过，比后面的都重要）

| 传什么 | 走哪条通道 | 实测数据 |
|---|---|---|
| 日常文件、代码、整目录、大文件 | **WiFi `192.168.0.50`**（补丁后已稳定） | 500MB / 34s / md5 一致，连做 3 轮共 1.5GB 零中断 |
| 装机、救砖、刷机、WiFi 完全不可用时 | **USB `172.16.42.1`** | 3MB / 0.52s / md5 一致 |
| 手机上要传给电脑（如备份） | 同上，反向 scp | — |

> **✅ 2026-11-21 23:10 更新：WiFi 大传输限制已解除**。ath10k A-MSDU 补丁已编译进新模块并热替换到正式位（见 §6.4），实测 **500MB 走 WiFi 连续传 34 秒 ×3 轮、共 1.5GB / 99 秒，零 `Connection reset`、dmesg 的 amsdu/recovery/crash 计数零新增**。现在日常维护**不需要插 USB 线**。USB RNDIS 保留为装机/救砖/WIFI 全挂时的唯一救命通道（配置见 §2 通道 B）。

**历史背景（补丁前的旧限制，现已不适用）**：补丁前 WCN3990 在持续数据流约 20 秒后会 RX 停摆（`device successfully recovered`），SSH 被 `Connection reset by peer` 打断；实测 500KB/3MB 都在 ~19.5s 断，限速无效。根因是 ath10k 驱动 A-MSDU 处理 bug（非硬件缺陷），已通过重编模块根治，详见 §6.4。

### 5.2 只改了几个文件（日常，最常用）

```bash
# 电脑上（Git Bash）
cd /d/AI/manju_agent/qq_bridge_official

# 1. 先看要推什么
git status --short

# 2. 传到手机临时区
scp -q src/plugins/doupo/core.py pmos@192.168.0.50:/tmp/push/

# 3. 落到正式位置（需要 sudo）
ssh pmos@192.168.0.50 'printf "123456\n" | sudo -S install -o pmos -g pmos -m 0644 /tmp/push/core.py /home/pmos/qq_bridge/src/plugins/doupo/core.py'

# 4. 重启生效
ssh pmos@192.168.0.50 'printf "123456\n" | sudo -S rc-service qq-bridge restart'
```

### 5.3 整目录同步（改动多时）

手机上**没有 `rsync`**（也没有 `curl`），所以别照抄网上带 rsync 的命令。用 tar 管道，一条命令推完：

```bash
# 电脑上（Git Bash），把整个 src/ 打包推过去并解包
cd /d/AI/manju_agent/qq_bridge_official
tar czf - --exclude='__pycache__' --exclude='*.pyc' src \
  | ssh pmos@192.168.0.50 'cd /home/pmos/qq_bridge && tar xzf - && echo SYNC_OK'

# 验证：看目标目录里最新几个文件的时间
ssh pmos@192.168.0.50 'ls -lt --full-time /home/pmos/qq_bridge/src/plugins/doupo/ | head -5'
```

只想推一个子目录就把 `src` 换成 `src/plugins/doupo`。

> ⚠️ 这一条**很可能超过 20 秒**（`src/` 压缩后约几 MB），按 §5.1 应该走 USB：
> 把命令里的 `pmos@192.168.0.50` 换成 `pmos@172.16.42.1`（先插好数据线）。
> 强行走 WiFi 的表现是传到一半 `Connection reset by peer`，白等 20 秒。

⚠️ **`data/` 和 `logs/` 绝对不要一起打包推送**。电脑上的 `data/` 可能比手机旧，覆盖过去就是数据回退事故。

### 5.4 改了 `.env`

### 6.4 WiFi 自愈机制（知道它在做什么，才不会误判）

> **✅ 2026-11-21 23:10 已根治（之前的"硬件缺陷/需 6.11 内核/只能自愈"全是误诊）**：`failed to extract amsdu: -11` 是 ath10k 驱动 bug——WCN3990 固件把一个 A-MSDU 拆成多个 HTT "in-order" indications，mainline 驱动直接丢弃 → 置 `rx_confused` → recovery → 链路不收包。上游补丁 `[PATCH v4] wifi: ath10k: make in-order rx amsdu buffers persistent`（David Heidelberg，2026-10）修复此问题，6.0 内核即可（不需要 6.11）。**本机已按此补丁重编 ath10k 模块并热替换，验收通过，详见本节末尾「A-MSDU 补丁部署记录」。**

这台手机**历史上**在持续大流量下行（实测 0.6~1.2MB 单流，或**任何持续约 20 秒的传输**）后会 `failed to extract amsdu: -11` → 整条链路不收包 → `device successfully recovered`（内核重启固件，但 TCP 已断）。**该问题现已由 ath10k 模块补丁根治**，下列 `wifi-watchdogd` 自愈机制继续保留作双保险（应对其它偶发断连），但不再需要为 A-MSDU 停摆而插 USB。

**A-MSDU 补丁部署记录（2026-11-21 23:02-23:10，已验收）**：
- 补丁适配到 6.0 源码（`htt.h` 加 `rx_in_ord_split` 暂存结构；`htt_rx.c` 的 `rx_free`/`rx_alloc`/`in_ord_ind` 暂存未完成 MSDU，下次 indication 续上、`-EAGAIN` 不再 fallthrough 到丢弃、`default` 分支加 recovery）。构建脚本/源码在电脑 `D:/AI/tools/pmdocker/work/amsdu/`，配方在 `D:/AI/tools/pmaports/device/archived/linux-postmarketos-qcom-msm8998/`（pkgrel 3→4）。
- 🔴 **关键认知：补丁编进的是 `ath10k_core.ko.xz` 模块（内核 config `CONFIG_ATH10K=m`、`CONFIG_ATH10K_SNOC=m`），不在 vmlinuz！所以根本不需要刷 boot.img / dd sde40。** 之前为"新内核比原内核大 11 字节"写的 `repack_bootimg2.py`（重排 DTB）是在错误假设上做的，**已作废、勿用**。
- 替换链路：新模块 vermagic `6.0.0 SMP preempt mod_unload modversions aarch64` 与手机原模块逐字一致、188 条符号 CRC 逐条一致（用 ELF `__versions` 段解析对比，零差异）⇒ 可直接 insmod。备份原模块在 `/home/pmos/ath10k-backup-20261121-230434/`（含 `ROLLBACK.sh` 一键回滚）。
- 热替换：`nmcli connection down` → `rmmod ath10k_snoc/core` → `cp` 新模块到 `/lib/modules/6.0.0/kernel/drivers/net/wireless/ath/ath10k/` → `depmod 6.0.0` → `modprobe ath10k_snoc` → `nmcli connection up`。全程走 USB RNDIS 通道操作（避免断自己的 WiFi SSH）。
- **验收**：WiFi 连续推 500MB ×3 轮（34s/34s/31s，共 1.5GB/99s），`scp exit=0`、md5 一致、dmesg 的 `failed to extract amsdu`/`device successfully recovered`/`firmware crashed` 计数零新增（仍是加载前的 4/6/6 历史值）、网关 0% 丢包。
- 开机自动生效：模块已在正式位且 `depmod` 已跑，开机内核自动加载的就是新模块，**无需额外开机脚本**。（未做整机断电重启的端到端验证，避免打断生产；模块自加载链路由上述事实保证。）

**自愈由 `wifi-watchdogd` 负责**（常驻，`/usr/local/bin/wifi-watchdogd`）：

- 每 **10 秒** ping 一次网关；
- 连续 **2 轮**（≥20s）不通 → 执行 `nmcli connection up FourSeasons_Plus_XA`（重新认证+关联，8~12s 恢复）；
- 只有 `wlan0` **设备本身消失**且连续 8 轮、`usb0` 不在线、30 分钟内没重启过，才会 `reboot`。

实测时间线：故意打崩 → 40s 检测 → 12s 重连 → bot `RESUMED`。全程无人干预。

### 7.3 剧本一：群里发命令，机器人不回

| 步骤 | 命令 | 判据 |
|---|---|---|
| 1 进程活着吗 | `sudo rc-service qq-bridge status` | `started`；不是就 `restart` 并看 err.log |
| 2 连上 QQ 了吗 | `tail -30 logs/service.log \| grep -E "connected\|RESUMED\|ws_down"` | 有 `Bot ... connected` 才算连上 |
| 3 收到群消息了吗 | `tail -20 logs/service.log \| grep GROUP_MESSAGE_CREATE` | 有 = QQ 侧正常，问题在业务逻辑；没有 = 连接/白名单问题 |
| 4 命令被匹配了吗 | `grep "Matcher" logs/service.log \| tail -5` | 没有 Matcher 行 = 口令没进白名单或没加载 |
| 5 业务抛异常了吗 | `tail -40 logs/qq_bridge_error.log` | 有 Traceback 就按堆栈改 |

常见真因：① 网络断（看 `网络` 业务）② 官方通道配额到点（`OFFICIAL_DAILY_GROUP_LIMIT`）③ 出图失败（`render_*` 抛错，看图码模块）④ 进程在但事件循环卡死（`py-spy` 没装，改用 `kill -QUIT` 打栈或直接 restart）。

**现象**：`rc-service qq-bridge restart` 成功、`pid` 会变，但 `/api/qqo/status` 一直
`online:false, bots:[]`。`logs/service.log` 里能看到一次：

```
[ERROR] nonebot | QQ | Failed to get gateway info.
httpx.ConnectError: [Errno -3] Try again
```

之后**没有任何重连日志**——nonebot 的 QQ 适配器拉 gateway 只试一次，失败就放弃，
整个进程还活着、进程内事件循环也正常，所以看门狗（只看 wlan0/网关）不会动它。

**为什么 2026-11-25 加的 DNS 守卫没兜住（2026-11-27 09:4x~09:5x 二次事故）**：

| 误判 | 实测 |
|---|---|
| 以为「DNS 通了」就够了 | 守卫只验 `bots.qq.com`，但拉 gateway 走的是 `api.sgroup.qq.com`，两个子域在 dnsmasq 里是**各自独立**的缓存项 |
| 以为失败是 DNS 慢 | 现场量：新进程连续 12 次 `getaddrinfo("api.sgroup.qq.com")` 全部 20~40ms 成功；同时 `wget https://api.sgroup.qq.com/` 却报 `bad address`、`httpx` 直连又拿到 `HTTP 404`。→ **间歇性**，不是稳定慢 |
| 以为守卫放行就万事大吉 | `DNS ready after 0 checks` + 三个域名全通 + 随后 `nc -z api.sgroup.qq.com 443` 连打 3 次全 ok，**但同一次启动的适配器仍然 gateway 失败** |

结论：**「DNS 热」不等于「射频醒」**。dnsmasq 命中缓存时根本没出网卡，手机 WiFi
省电休眠下**第一发真实报文会丢**，而适配器只试一次。

**加固（`deploy/phone/qq-bridge.init`，2026-11-27 已装机，旧版备份
`/etc/init.d/qq-bridge.bak-20261127`）**：启动前置三道守卫，任一不过就等，最多 20 轮 ×3s。

```bash
# ① 默认路由
while [ $i -lt 40 ]; do ip route | grep -q '^default' && break; sleep 3; i=$((i+1)); done

# ② DNS：适配器会碰的域名逐个验到「全部」可解析（不再只验一个）
_dns_hosts="bots.qq.com api.sgroup.qq.com api.qq.com"

# ③ 出网 TCP 握手：真实连一次 443，既唤醒射频又验证整条出网路径
nc -z -w 5 api.sgroup.qq.com 443 && nc -z -w 5 bots.qq.com 443
```

正常全热时三道都是 `after 0 checks`；冷启动最多等 60s。装好后重启一次即上线
（`pid=10435, bots=['1906371548']`）。

**处置口诀**：见到 `Failed to get gateway info` → **别反复 restart 赌运气**，
先 `nc -z -w 5 api.sgroup.qq.com 443` 确认真能出网，再 restart 一次即可；
若 `nc` 也不通，说明是链路问题，按剧本二走。

### 7.7 剧本五：怀疑崩溃过 / 想看重启原因

### 7.8 剧本六：存档看起来「丢了」

### 7.9 剧本七：8099 的 `/qq-official` 前台卡在「正在连接本地控制台…」

**先分清两件事**（2026-11-22 实测，很容易误判成「手机连不上」）：

| 页面区域 | 数据来源 | 说明 |
|---|---|---|
| 顶部状态栏（温度 / CPU / 内存 / 开机时长） | `8099 /api/phone/status` → SSH 采集手机 | 这块有数 = **手机是通的** |
| 中间大块控制台（运行态 / WiFi 健康 / 主机资源） | **iframe 嵌 `127.0.0.1:8097`** | 卡在「正在连接本地控制台…」= **8097 适配层没在跑**，不是手机的问题 |

**排查（在电脑上）**

```bash
# 1) 手机通不通（只要这个 200 且 ok:true，手机就没问题）
curl -s http://127.0.0.1:8099/api/phone/status | head -c 200

# 2) 8097 适配层在不在（关键）
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8097/api/status   # 200 = 正常
netstat -ano | grep ":8097 .*LISTENING"                                    # 应有监听

# 3) 8099 在不在
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8099/qq-official
```

**修法**：8097 由 `web_app.py::main()` 在 8099 启动时自动拉起。它没在跑，就**重启 8099**：

```bash
# Windows：结束 web_app.py 进程后重新启动
# cd D:/AI/manju_agent && server/.venv/Scripts/python.exe web_app.py
```

重启后核对日志 `D:/AI/logs/web_app.log`（或 `D:/AI/manju_agent/logs/web_app.log`，取决于启动时的工作目录）应出现：

```
>> 手机控制台适配层已拉起 (127.0.0.1:8097, ...\server\phone_console.py)
```

**两个已修掉的真实缺陷**（2026-11-22，别改回去）：

1. `_ensure_phone_console()` 原来只做 TCP `connect` 探活 —— 端口被半死进程占着时 `connect` 成功，就被误判成「已在运行」直接 return，**永不重拉**。已改为探 `http://127.0.0.1:8097/api/status` 必须返回 200，且 Popen 后还要 HTTP 验证真的活了才报成功。
2. `phone_console.py` 的 `ThreadingServer` 原来没有 `handle_error` —— 浏览器每次关 iframe 就打一坨 `ConnectionAbortedError` traceback。已加 `handle_error` 吞掉 `ConnectionReset/ConnectionAborted/BrokenPipe`。

> ⚠️ 另一个坑：Windows 环境变量里如果**同时**存在 `HTTPS_PROXY` 和 `https_proxy`（大小写重复），PowerShell `Start-Process` 复制环境时会因字典键冲突直接报 `ArgumentException`，看起来像「启动了没反应」。用 `Start-Process` 前先 `$env:https_proxy=$null; $env:http_proxy=$null; $env:HTTP_PROXY=$null`。

## 8. 危险操作黑名单（每一条都出过事）

| 禁止 | 原因 | 后果 |
|---|---|---|
| `unbind` / `bind ath10k_snoc`（或任何 `echo ... > /sys/bus/.../drivers/.../unbind`） | WCN3990 被异常拆除后 QMI 拒绝提供 MSA（`msa info req rejected: 90`） | probe 永久失败、`wlan0` 消失、**只能重启**。19:33 那次就是这么挂的 |
| `nmcli device reapply` | 停摆时 NM 报 `Device is not activated`，无效且搅乱状态 | 白折腾，会误以为网卡坏了 |
| `nmcli connection down` | 主动断链路 | 5GHz-only 的 SSID 不一定能立刻重新关联 |
| 把 `802-11-wireless.band` 钉成 `bg` | 这个 SSID **只有 5GHz（信道157）** | 永久连不上，只能 USB 进去改回来 |
| 删 `DOUPO_DATA_PATH`/`XIUXIAN_DATA_PATH` | 插件回落示例库 | 老玩家被要求「重新入道」（20:15 事故） |
| 打包推送时把 `data/` 或 `logs/` 一起覆盖过去 | 覆盖生产存档 | 数据回退，不可逆 |
| `docker` 相关任何操作 | 这台机器没有 docker | 报错浪费时间；真正的服务在 OpenRC 里 |
| `apk add` 装 Python 包 | pmOS 源国内不可达 + musl 不认 manylinux 轮子 | 装不上；正确做法见 §9 |
| 长期满电插电 | 电池鼓包 | 硬件损坏 |

## 9. 附录：装新 Python 包（唯一正确姿势）

Alpine 是 **musl libc**，pip 会直接拒绝 manylinux 轮子，报错长得像「找不到某个依赖」（例如 `Could not find a version that satisfies jiter`），**不是**网络问题。

正确流程（在电脑上拉 musl 轮子 → 传过去离线装）：

```bash
# 1. 电脑上（Docker 用来下载目标平台的轮子）
docker run --rm -v /d/AI/tools/wheels:/w python:3.13-slim \
  pip download <包名> -d /w --only-binary=:all: \
  --platform musllinux_1_2_aarch64 --platform musllinux_1_1_aarch64 \
  --python-version 3.14 --implementation cp --abi cp314 --abi abi3 --abi none

# 2. 传上手机
scp -r /d/AI/tools/wheels pmos@192.168.0.50:/tmp/

# 3. 手机上离线装
/home/pmos/venv/bin/pip install --no-index --find-links /tmp/wheels <包名>
```

`--abi abi3` **必须带**，否则 `jiter`（openai 的依赖）这类 abi3 轮子会漏拉。

**当前已装的关键包**：`nonebot2 2.5.0`、`nonebot-adapter-qq 1.7.4`、`nonebot-adapter-onebot 2.4.6`、`openai-agents 0.25.0`、`pillow 13.0.0`、`httpx 0.28.1`。
