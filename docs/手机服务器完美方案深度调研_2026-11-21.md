# 手机 24 小时服务器「完美方案」深度调研

> 时间：2026-11-21
> 触发：用户质疑 Android+Termux 杀后台风险，要求找"完美方案和系统"，做深度调研。
> 目标机型：小米 6 / sagit / MSM8998 / 6GB。
> 结论先行：**穷举所有系统后，没有绝对完美；但对"真 Linux + 无杀后台 + 联网"这个核心诉求，sagit 上唯一的正解是 postmarketOS，而且之前判它死刑是错的——WiFi 不是硬件坏，是服务没配齐 + 内核旧。**

## 二、为什么 Ubuntu Touch 不是答案（看起来最美，实则坑）

Ubuntu Touch 在 sagit 上页面很好看（WiFi/Hotspot/Bluetooth 全 working、24h 电池、7 天稳定），但三个硬伤直接否掉：

1. **rootfs 是只读 immutable 镜像**，官方明确"apt-get not working by design"。开 rw（`mount -o remount,rw /`）只是开发调试用，会破坏增量 OTA，官方建议定期重刷。→ **没法稳定装 Python/pip/qq_bridge 依赖**。
2. 只能跑 Libertine 容器（跑 GUI 桌面 app 用）或 Docker（社区 gist，vfs 存储驱动、需改 systemd，很脏）。→ 部署 qq_bridge 绕一大圈。
3. sagit 端口状态：**Basic support**，维护者"Inactive since 2025-10"，蜂窝（calls/SMS/data）全 not working。→ 长期维护存疑。

结论：Ubuntu Touch 适合"当手机用"，不适合"当任意服务的服务器"。

## 三、核心发现：pmOS 的 WiFi 不是硬件死路，是我们没配完

之前的判断"WiFi 硬阻塞"需要修正。查证链：

1. **msm8998 SoC wiki 明确写 WiFi = Works**，并给出完整启用步骤。
2. **sagit wiki 主线段也列 WiFi 为 working**，XDA 有 sagit 实机截图确认。
3. **根因不是固件**：我 SSH 实读手机，`wlanmdsp.mbn`(2.7MB) + `modem.mbn`(56MB) 都在 `/lib/firmware/qcom/msm8998/xiaomi/`，符合 wiki"两者必须同目录"的要求；`firmware-5.bin` 60 字节是正常占位。
4. **真正的两个缺口**：
   - **用户态服务没配齐**：wiki 要求装并启用 `pd-mapper`、`tqftpserv`、`qrtr`、`rmtfs`，且先跑 `diag-router`。实测手机只装了 `tqftpserv`、`rmtfs`，`pd-mapper`/`qrtr` 缺失。之前 dmesg 的 `node with id 0 not found in QRTR bus` 正是缺 qrtr 总线的症状！
   - **内核太旧**：我们刷的是 6.0-r3。MSA ready indication 补丁是 **Linux 6.11** 才进主线（`737abcabe` commit），6.0 需要额外 fake MSA 补丁。

### 修复路径（两条，都不用放弃 pmOS）

- **路径 C1（最新内核）**：用 degdag 的 `W.I.P_sagit_mainline` fork 重建 6.11+ 内核，按 wiki 配齐 4 个用户态服务 + diag-router。优点：一劳永逸、主线长期更新。缺点：要编译内核（1-3h）。
- **路径 C2（当前 6.0 内核 + fake MSA）**：给 6.0 内核打 fake MSA 补丁 + 配齐服务。优点：不用重编整套系统。缺点：补丁需自己移植。

> 无论 C1/C2，第一步都该先做**零成本的验证**：在现有镜像上 `apk add pd-mapper qrtr`（补装缺失服务）+ 启动 diag-router + 启用服务，看 wlan0 是否能出来。出得来 → 连内核都不用换，pmOS 直接可用。

### 实测验证结果（2026-11-21 12:xx，已在手机上执行，可逆）

按上述步骤实测，结论明确：

1. **服务层已全部修好**：从电脑侧下载 `pd-mapper`/`qrtr`/`qrtr-libs` 三个 apk（手机无外网，用 SFTP 推送 + `apk add --no-network --allow-untrusted` 离线装），四个服务全齐。启动 `diag-router` 后 **`qrtr-lookup` 能看到 QRTR 总线上的 MODEM/WCNSS/LPASS DIAG 服务**——之前 `node with id 0 not found in QRTR bus` 的症状消失。
2. **但 wlan0 仍出不来，modem 仍 offline**：手动 `echo start > remoteproc0/state` 触发 MSS，dmesg 明确：`MBA booted, loading mpss` → `qcom-q6v5-mss 4080000: start timed out` → `Boot failed: -110`。
3. **定性**：服务层问题已排除，剩下的就是**内核层的 MSA-ready indication 缺陷**（wiki 明说 Linux 6.11 commit `737abcabe` 才修复）。6.0 内核必现超时。

**⇒ 最终确定：pmOS 路线要通，必须升级/重编内核到 6.11+（或给 6.0 打 MSA 补丁）。服务配置不是障碍了，已验证修好。**

**可逆性**：验证后已回滚——停掉手动起的 pd-mapper/diag-router、删除 boot runlevel 改动、清理临时脚本；四个 apk 包保留（无害，修内核后可直接用）。手机仍无 wlan0、remoteproc0 仍 offline，与验证前一致。未刷机、未清数据。

**下一步（需用户拍板）**：走 C1 重建 6.11 内核（degdag 的 `W.I.P_sagit_mainline` fork + MSA 补丁），这是把 pmOS 变成完美方案的最后一块拼图；编译约 1-3h，全程在电脑/pmbootstrap 环境，不碰手机现有系统，编译好先 `fastboot boot` 临时验证再决定是否 flash。

## 五、行动建议（不踩坑版）

1. **先做零成本 WiFi 验证**（可逆、不动系统、10 分钟）：在现有 pmOS 上补装 `pd-mapper`/`qrtr`、启动 `diag-router`、rc-update 启用四服务，看 wlan0 能否出现。
   - 成功 → pmOS 就是完美方案，直接部署 qq_bridge（原生 Python，无需 Docker）。
   - 失败（remoteproc 仍超时）→ 走 C1 重建 6.11 内核，或退回 Termux。
2. **不刷 LineageOS/Ubuntu Touch**：前者有杀后台，后者 rootfs 只读，都不满足"完美"。
3. 无论哪条路：外部存活监控 + 定时备份 + 电池限充 80% + 摘壳散热，这几条不变。
