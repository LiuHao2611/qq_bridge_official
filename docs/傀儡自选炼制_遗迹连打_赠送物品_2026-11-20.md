## 1. 自选材料：只造一条临时配方，其余全走老路

### 1.1 为什么不是「新开一条炼制分支」

固定配方链路里已经有五道硬东西：

1. 木桶判档 `recipe_tier(slots) = min(五维) − 1`（唯一入口）；
2. 五道资格闸 `puppet_gate()`（境界 / 灵魂 / 炼药等级 / 异火 / 竹简）；
3. `craft_checks()`（躯体新鲜度 E10、神智 E15）；
4. 扣料 `take_materials()` + 扣斗气；
5. 落库 `make_puppet()` + `add_puppet()`。

新开分支最容易把 1、2 写漏（第九轮之前 `first_craft_tier` 被弃用就是同类事故）。
所以自选只做一件事：**根据四维造一个带 `custom: True` 的临时配方 dict**，
后面 100% 复用原链路。命令层只有一处分支：

```python
if arg.startswith("自定"):
    rec, custom_err = pc.custom_recipe_from_arg(arg, p_view)
    if rec is None:
        return custom_err
    lack = pc.missing_materials(mats, rec)
elif arg:
    rec = pc.recipe_by_name(arg)          # 固定配方，逐字节不变
```

### 1.2 火不自选（第一版真 bug）

第一版给临时配方写死 `"fire": "B"`。结果 `recipe_slots(rec)` 在没有 `p` 的调用里
（单测、卡面反查）读这个字母，木桶判档被凭空拉低一档：斗宗躯 + 七阶核 + 斗宗魂 +
寒铁本该地级，被判成人级，玩家还会看到一句假的「本可出地级，但你的火只到兽火」。

修法两条一起上：

* 解析器按玩家实况取火 `g = fire_grade(p)["grade"]`，`S/A/B` 如实写；
* 命令层 `nominal` 对 `custom` 配方直接取 `tier`，不拿占位火算「本可出 X」。

守门 `test_no_shortcut_through_tier` + 注入 #5/#6 钉住这两条。

### 1.3 材料名必须落在分档表里

`slot_tier(kind, name) <= 0` 即判非法，报「「XXX」不是有效的躯体材料」并给出
`发「炼制傀儡 自定」看清单`。**不许静默回落人级** —— 玩家写错一个字就白烧四份料，
是最不能接受的失败方式。清单来自 `PUPPET_BODY_TIERS` / `PUPPET_CORE_TIERS` /
`PUPPET_SOUL_TIERS` / `PUPPET_METAL_TIERS` 四张表，没有第二份手写名单。

### 1.4 参数顺序错位是最可能的回归

注入 #8 把 `"body": parts[0]` 改成 `parts[1]`，守门立刻红 9 条 —— 因为测试断言
落库的 `body_name / soul_source / metal_name` 与玩家选的**逐个相等**，而不是只看「炼成了」。

## 2. 遗迹自动连打：力竭就是 `fight` 自己改完的 hp/mp

### 2.1 不新造「力竭」判定

`core.fight()` 本来就原地改 `p["hp"] / p["mp"]`，所以循环里连打天然实现力竭：

```python
while idx < total:
    mon = core.monster_scaled(p, sg, puppet_bonus=bonus)
    res = core.fight(p, mon, puppet=pu, formation_n=n, puppet_flame_mult=flame_mult)
    if not res["win"]:
        ... break
    idx += 1
```

不引入「气血归零 / 斗气归零」新判据：这两个字段在战斗里并不判负（斗气见底转普攻），
另造一套只会与 `fight` 的胜负口径打架。

### 2.2 三条防刷

| 防线 | 做法 | 注入组 |
|---|---|---|
| 输了不发料 | `drops = dict(sg["drops"]) if win else {}` | #4 |
| 水位线只升不降 | `ruin_clear(qq, day, idx + 1)`，且只在胜场后调用 | #3 |
| 全通后不再打 | 入口先判 `int(st["stage"]) >= total` 直接返回 | 既有测试 |

材料只在胜场那一段 `add_material`；力竭段一个都不发（守门逐项断言弱号打完后
`PUPPET_MATERIALS` 全为 0）。

### 2.3 两处必须传真实 `p`

怪血反解与实战出手必须是同一个玩家，否则「带傀儡反而吃亏」：

```python
bonus = pc.puppet_expected_damage(pu, n, flame_mult=flame_mult, p=p)   # 反解
res = core.fight(p, mon, puppet=pu, formation_n=n,
                 puppet_flame_mult=flame_mult)                          # 实战
```

这条行为测试抓不住（lv96 强号用标尺玩家反解也照样赢），所以另加源码级钉子
`test_source_gates`，注入 #7 就是靠它抓的。

### 2.4 自动服药：整趟共用一份预算（`PUPPET_RUIN_PILL_CAP = 2`）

六段连打最容易出的两个隐性事故：

1. `fight` 默认 `auto_pill=True`、每场最多 2 颗，六段一趟能吞掉十几颗回灵丹，
   **玩家完全不知情**（菜单全量测试就是这么发现的：跑到「锁定 回灵丹」时包里已经空了）；
2. 丹药一多，「力竭」永远不会到来 —— 自动连打变成无限续杯，与用户要的
   「力竭为止」正好相反。

做法：和 `core` 里多敌连战同一写法，**循环外**建一份 dict 整趟共用：

```python
pill_budget = {"hp": 0, "mp": 0, "cap": int(cfg.PUPPET_RUIN_PILL_CAP)}
...
core.fight(p, mon, ..., pill_budget=pill_budget)
```

`fight` 会就地累加 `pill_used`，所以 cap 是**跨段累计**的硬顶：整趟最多 2 颗，
够救一次急，不会洗空包裹。建在循环里就等于每段重置，守门用
`body.index("pill_budget = {") < body.index("while idx < total:")` 钉死这一点。

顺带修掉 `core` 一个 falsy 坑：`pill_cap = int(pill_used.get("cap") or ...)` 让
`cap=0`（「本场一颗都不许自动吃」）静默回落成默认 2 颗，封 0 封不住。
改成 `if "cap" in pill_used` 判定。既有调用点传的都是 ≥1，行为不变。

### 2.5 一处输出=一条消息

六段战报全并进同一张遗迹卡：`build_ruin_data()` 的「本次挑战」分组里一段一行
（`第 N 段 … ｜ 结果 ｜ 回合`），head 只写「第 N 段力竭 / 今日全通」。
守门 `n_rows == len(runs)` 防漏段，`render_ruin_for()` 断言真出 PNG。

## 3. 赠送：一次事务写两行，否则物品会凭空消失

### 3.1 旧写法的真实危害

`cmd_give`（金币）是两次独立 `put_player`：

```python
await store.put_player(p)     # 事务 1，已 commit
await store.put_player(to)    # 事务 2，抛 StoreError
```

第二步失败时第一步已经落库：**金币/物品凭空消失**，玩家只看到「送失败」。
金币是小事，物品是玩家的材料，必须一次成功或一次不做。

### 3.2 `Store.transfer_item()`：一个 `_tx()` 写两行

```python
with self._tx() as con:
    self._upsert_player(con, src_qq, a, sa, now)
    self._upsert_player(con, dst_qq, b, sb, now)
```

失败整段 rollback，并且**就地回滚内存**：

```python
bag_a.clear(); bag_a.update(before_a)
bag_b.clear(); bag_b.update(before_b)
```

不能 `a["bag"] = before_a` —— 项目里 `get_player()` 返回的是**活字典**，36 个调用点
都持有它的引用，换对象会让别人手里的引用永远停在旧内容。守门直接断言
`pa["bag"] is live_a`（注入 #4 就是抓这个）。

### 3.3 能送什么

候选池取**自己包裹里真实有的**键（`core.bag(p)`），不是宝库目录：

* 丹药 / 药材 / 天材地宝 / 炎星石 / 药渣 —— 全部可送；
* 目录里有但自己包里没有的（如「血灵草」）—— 拒绝，回「包裹里没有【X】」；
* 模糊匹配「回灵」→ 回灵丹（与 `_match_item_name` 同策略，先精确再包含）。

**傀儡材料不在这个池子里**：它们在独立库 `data/doupo/puppet_data.sqlite` 的
`puppet_materials` 表，与 `doupo.sqlite` 跨库，无法进同一个事务。要做就得
先设计「两库补偿」而不能顺手加，故本轮明确不做（见 §6 待定）。

### 3.4 解析口径

`commands.parse_gift(text)` 是纯函数，只认 ASCII 数字：

| 输入 | 结果 |
|---|---|
| `送 100` | 金币 100（旧路径） |
| `送 回灵丹 5` | 回灵丹 ×5 |
| `送 回灵丹×5` / `x5` / `*5` | 回灵丹 ×5 |
| `送 回灵丹` | 回灵丹 ×1 |
| `送回灵丹5` | 回灵丹 ×5（无分隔符） |

入口 `give` handler 按 `if item:` 分流到 `cmd_gift`，否则回 `cmd_give`。
数字不再用 `_num(event)`（那条取全文第一个数字，官方通道把 @ 解析成 openid 后
容易把一串数字当金额），统一从 `get_plaintext()` 解析。
守门 `test_source_gates` 钉住 `if item:` 本身 —— 注入 #13 把条件改成 `if False:`
时，只查「有没有调用 cmd_gift」是抓不到的（那正是白守）。

### 3.5 失败一律零副作用

| 情况 | 行为 |
|---|---|
| 数量 ≤ 0 | 「数量无效」，双方包裹不动 |
| 超过持有量 | 「只有 N 个，不够送 M 个」 |
| 送自己 | 「不能赠送给自己」 |
| 对方未入道 | 「对方尚未入道」 |
| 缺 @ 目标 | 用法（同时给出金币写法） |
| 写盘失败 | `StoreError` + 双方回滚 + 磁盘未变 |

守门对每一种都断言 `bag` 快照逐键相等，不是只看返回文字。

## 4. 本轮踩坑

1. **占位 B 火把木桶判档拉低一档**（§1.2）—— 临时配方里的火必须写玩家实况。
2. **`if item:` 的分流条件本身才是红线**：只断「调用了 `cmd_gift`」时，
   `if False:` 能静默让物品入口变成死代码（注入 #13 白守 → 补条件断言）。
3. **`while` 改 `if` 只能靠行为测试抓**：`test_source_gates` 之外，
   `len(runs) >= 2` 才是真正区分「连打」与「单段」的断言。
4. **回滚不能换 dict 对象**（§3.2）。
5. **金币模式与物品模式必须互斥**：`送 100` 若被当成物品名，旧功能立刻失效；
   反过来，物品被当金额会让玩家白送一堆金币。

## 6. 待定（需要拍板）

**傀儡材料能不能送？** 它们在 `puppet_data.sqlite`，与玩家存档不在同一个库，
无法进同一事务。可选方案：

* A. 只做「同一库内的物品」，傀儡材料走「赠送凭证」——收件人自己去遗迹/商店兑换；
* B. 接受跨库「先扣后加 + 失败补偿日志」，用重试队列补写（复杂，且要有对账脚本）；
* C. 把傀儡材料并进 `doupo.sqlite`（会动库路径单源红线，牵动 11 条守门）。

本轮按 A 的范围交付（只送 `doupo.sqlite` 里的背包物品）。
