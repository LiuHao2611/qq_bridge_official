## 六、生产事故：重启后 `online:false`（这次不是 DNS 慢）

部署后 `status` 一直 `online:false, bots:[]`，`service.log` 里一次
`Failed to get gateway info / httpx.ConnectError: [Errno -3]`，之后**再无重连**——
nonebot 的 QQ 适配器拉 gateway 只试一次，失败即放弃，而进程本身活着，看门狗不会动它。

排查把上一轮的结论推翻了一半：

| 原以为 | 现场实测 |
|---|---|
| 2026-11-25 加的 DNS 守卫会兜住 | 守卫只验 `bots.qq.com`，但 gateway 走 `api.sgroup.qq.com`，**两个子域缓存互不相干** |
| 失败 = DNS 冷缓存慢 | 新进程连打 12 次 `getaddrinfo(api.sgroup.qq.com)` 全部 20~40ms 成功；同一时刻 `wget` 报 `bad address`、`httpx` 却拿到 `HTTP 404` → **间歇性**，不是稳定慢 |
| 守卫放行就安全 | `DNS ready after 0 checks` + 三域名全通 + `nc -z ... 443` 连打 3 次全 ok，**同一次启动的适配器仍 gateway 失败** |

真因：**「DNS 热」不等于「射频醒」**。dnsmasq 命中缓存时根本没出网卡，WiFi 省电休眠下
第一发真实报文会丢，适配器只试一次 → 一命不续。

**加固**（`deploy/phone/qq-bridge.init`，已设备份 `qq-bridge.bak-20261127`）：
启动前三道守卫——① 默认路由 ② 适配器会碰的三个域名**逐个**验到全部可解析
③ **真实 TCP 443 握手**（`nc -z`）既唤醒射频又验整条出网路径。装好后重启一次即上线
（`pid=10435`）。脚本已纳入仓库 `deploy/phone/qq-bridge.init` 版本管理，不再只存在于手机上。

> 诚实说明：②③ 之后重启一次即成功，而之前仅 DNS 守卫的两次重启都失败——数据点少（n=1 vs 2），
> 但 TCP 握手探测在逻辑上严格强于纯 DNS 探测，且直接对上了「第一发报文丢」这个机制。
