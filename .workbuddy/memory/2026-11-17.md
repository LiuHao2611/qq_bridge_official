## 爬塔「气血好像没降低」= 回血口径，不是重置（用户反馈后修）

用户原话：`看看日志，气血怎么好像没降低呢，是不是每次爬塔就重置状态了`

**结论：不是重置**。`temp_hp` 每层写回 `st` 并 `save`，第 N+1 层进场血量 = 第 N 层剩余，
逐层打印可证。真因是 `FLOOR_REST_HEAL = 0.35` 每层白送 35% 上限，而单层掉血常只有
10~30% → 回血把伤害**全部盖掉**。实测 lv60 连爬 8 层每层都 `34400/34400`（满血），
玩家视角就是"没掉血/像重置"。

### 修法（两手必须一起改）
1. `core.tower_floor` 回血加硬约束：`rest = min(cap*0.12, 本层实际损失*0.5)`，
   无伤不回 → **跨层气血单调不增**（`FLOOR_REST_DMG_RATIO = 0.5`）。
2. `TOWER_ATK_SCALE 0.42 → 0.18`。回血不再兜底后，0.42 会让 lv70 只剩 6~7 层；
   实扫（tmp/evidence/tower_scale_sweep.py，不入库）选定 0.18。

修后保守曲线（连战不选回血战利品）：lv10 7 / lv30 8 / lv50 9 / lv70 13~14 / lv100 19 层，
终局剩 15~20% 气血。真实命令逐层：lv30 9957→5687(8层)，lv60 33029→13802(12层)。

### 口径边界（别写错断言）
* 只有**不带战利品**时才单调不增。三选一的「回春散」主动回血、「吸血+12%」战斗中回血，
  气血上涨是玩家自己选的续航，不是 bug。门禁 `test_hp_monotonic_across_floors` 按此界写。
* 曲线门禁改用**中位**判「见得到第 10 层」：lv70 偶发 9 层（Boss 词缀歪），拿 max 当门槛
  会把正常波动判红；无限层失控仍看 max < 200。

### 回退验证

## 爬塔层数被清零事故（我的锅）+ 会话落盘修复

用户原话：`我发现爬塔层数被你重置掉了，你是不是没把爬塔数据保存好`

**真因**：`TowerStore` 只存进程内存（仿 duel 的"临时会话不落盘"）。我为了调平衡
连续 `up -d --build` 重建容器 3 次，每次新进程 → 正在爬的层数/气血/增益全没。
用户体感就是"层数被重置"。**不是没保存好，是根本没保存。**

### 修法
1. 会话落盘 `config.TOWER_SESSION_PATH`，默认与 `doupo.json` 同目录：
   容器 `/app/data/doupo/tower_session.json`（卷内），宿主 `data/doupo/tower_session.json`。
   可用 `DOUPO_TOWER_SESSION_PATH` 覆盖。**不从 `__file__` 推目录**（会被烘进镜像）。
2. 原子写：同目录 `.tmp` + `flush`+`fsync` + `os.replace`；**写失败抛错 + ERROR 日志**，
   不静默降级（否则就是"看着存了其实没存"，正是这次事故的性质）。
3. TTL 900s → **21600s（6 小时）**：会话已持久化，15 分钟太短。
4. **超时补结算**：过期会话移入 `_expired` 队列，`爬塔/塔层/塔结算` 任一入口先补结算
   再开新轮 —— 早期实现是直接把过期会话删掉，等于挂机久了白爬。

## 14:00-14:20 玩家存档 JSON → SQLite 迁移（用户「玩家数据肯定是要存到库里」）

### 为什么换（写进 store.py 顶部注释了，别重犯）
1. **写放大**：`put_player` 走 `save()` → 整份 `json.dump` 全服存档；斗破有 36 个写入点，
   1000 玩家时每敲一条命令重写 ~700KB。
2. **并发即丢档**：`asyncio.Lock` 只在**进程内**有效。第二个实例/测试脚本/运维手工改档
   = 后写覆盖，输的那方静默丢失（`media_assets.json` 被测试覆盖就是同类事故）。
3. **断电靠人恢复**：旧 `_write()` 只 `close()` 无 `flush+fsync`，宿主断电可能截断，
   只能靠 `.corrupt-` 备份手工找。

### 实现（`src/plugins/doupo/store.py`、`src/plugins/xiuxian/store.py` 全重写）
* 一人/一宗门/一群**一行**；`PRAGMA journal_mode=WAL` + `synchronous=FULL` + `busy_timeout`。
* `_tx()` 上下文：成功 commit、异常 rollback、**并 close**（不 close 在 Windows 下会让
  临时库删不掉 → WinError 32，xiuxian test_commands 就是这么红的）。
* 内存仍是权威态（`get_player` 返回活字典，36 个调用点不用改）；
  `put_player` 走单行 UPSERT，`save()` 走**兜底 diff**（内存 vs 快照）——
  AST 全量核过：项目里没有"改了不 put"的路径，兜底只为防未来写法。
* **不做自动回退**：出错抛 `StoreError`，绝不偷偷退回 JSON。
* 旧 JSON 只当一次性导入源：库空才导，`meta.imported_from` 防重复导（防"旧档诈尸"）；
  **原文件一个字节都不动**（它就是回滚备份）。

### 上线结果
* 导入：斗破 2 玩家/2 群，修仙 2 玩家/0 宗门/1 群/1 世界。
* 逐字段比对旧 JSON vs 新库：**差异 0 处**；两个 JSON 的 sha1 迁移前后完全一致。
* `docker diff | grep /app/data/` = 0（库在卷里）；启动无 ERROR；WAL 文件随连接关闭自动收起。

### 门禁 `tests/test_game_save_sqlite.py`（11 条，全部做过 mutation 回退验证）
导入只一次 / 原件不许动 / 写一人只写一行 / 就地改活字典 save 兜底 / 坏档先备份 /
写失败抛 StoreError / 等级迁移要落盘 / 真实存档导入零丢失（逐字段）。
* 回退①：去掉 `meta` 导入护栏 → `库里清空后又把旧 JSON 导回来（旧档诈尸）` 红。
  一开始没变红，查明是"只清 players 不清 groups"进不到导入分支 → 测试改成两个都清，
  再回退才红。**门禁没红 ≠ 门禁有效，必须确认它真的走到了那条路径。**
* 回退②：`save()` 直接 return → `就地改活字典丢档` 红。
* 回退③：导入后顺手把 JSON 规范化写回 → 2 条红（含现网存档被改写）。

### 回滚方法（写给自己）
旧 JSON 是**迁移那一刻**的快照，之后的进度只在库里。真要回滚：
```bash
python -c "import sqlite3,json;c=sqlite3.connect('data/doupo/doupo.sqlite');\
json.dump({'players':{r[0]:json.loads(r[1]) for r in c.execute('select qq,data from players')},\
'groups':[r[0] for r in c.execute('select group_id from groups')]},\
open('data/doupo/doupo.json','w',encoding='utf-8'),ensure_ascii=False,indent=1)"
```
再把 git 回退到迁移前那个 commit。
