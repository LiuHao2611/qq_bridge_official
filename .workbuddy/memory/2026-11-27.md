## §五 环境事故（非本轮代码）

部署后 `/api/qqo/status` 一直 `online:false`。根因：`Getaway info` 失败，
`httpx.ConnectError: [Errno -3] Try again` = musl `getaddrinfo` 返回 EAI_AGAIN。
`/etc/resolv.conf` 是 NM 的 dnsmasq（127.0.0.1），**冷缓存首次解析 2.5s**，启动瞬间 DNS 未热 → 适配器放弃。
处置：`nmcli connection up FourSeasons_Plus_XA` → 等 DNS 热（20 连测全 0ms）→ `rc-service qq-bridge restart` → 5s 上线。
教训：**`rc-service restart` 前后要确认 DNS 已热**，否则 QQ 适配器 `Failed to get gateway info` 后不会自愈。
另注：`warframe` 采集与 QQ 同一时刻失败，是判断「整机出网」还是「单服务」的现成探针。

**环境事故（推翻上一轮一半结论，重点）**
部署后 `online:false`。这次**不是 DNS 慢**：新进程连打 12 次
`getaddrinfo("api.sgroup.qq.com")` 全 20~40ms 成功；同一刻 `wget` 报 `bad address`、
`httpx` 却拿 `HTTP 404` → 间歇性。且 `DNS ready after 0 checks` + 三域名全通 +
`nc -z ... 443` 连打 3 次全 ok，**同一次启动的适配器仍 gateway 失败**。
真因：**「DNS 热」≠「射频醒」**——dnsmasq 命中缓存时没出网卡，WiFi 省电休眠下
第一发真实报文会丢，而 nonebot QQ 适配器拉 gateway **只试一次**，失败就一命不续
（进程活着、事件循环正常，看门狗只看 wlan0/网关，不会动它）。
加固 `/etc/init.d/qq-bridge`（已入库 `deploy/phone/qq-bridge.init`，旧版备份
`qq-bridge.bak-20261127`）：① 默认路由 ② `bots.qq.com api.sgroup.qq.com api.qq.com`
**逐个**验到全部可解析 ③ **真实 TCP 443 握手**（`nc -z`）唤醒射频 + 验整条出网路径。
加固后两次重启均一次上线（2/2）。**处置口诀**：见 `Failed to get gateway info` 不要反复
restart 赌运气，先 `nc -z -w 5 api.sgroup.qq.com 443`，通了再 restart 一次即可。
