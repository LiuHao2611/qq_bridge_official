## 二、① 力竭是假的 —— 确认属实，已改真

## 三、③ 层号矛盾 —— 两套语义混用

`st['floor']` = **已通过层**；`tower_floor` 的 `r['floor']` = **正在打的层**。
旧代码力竭时传 `res['floors']`（已通过层），于是 cp=24 → 从 25 开打、25 就输 →
「止步 24」。而周副本一直用 `r['floor']`（正确）—— 两处口径本身就不一致。

**修法**：`doupo_text.tower_down(fallen, cleared=None)` 一律报**倒下那一层**，
必要时附「此前已通 N 层」；`cleared<=0` 或相等时不附。爬塔 / 自动爬塔 / 周副本
全部改传 `r['floor']`；`_expired_settle_line` 的「止步第 N 层」改「已通第 N 层」
（超时场景没有倒下层）；「（最高 N 层）」改「（最远已通 N 层）」。

**关键自洽点**：`tower_checkpoint = cleared`，所以「checkpoint+1 = 出发层 = 倒下层」，
玩家读到的三句话现在严丝合缝：从 25 出发 → 倒在 25 → 再冲还是 25。

## 四、② 出卡变慢 —— 不是缓存没生效，是别处

### 日志实测（`~/qq_bridge/logs/qq_bridge.log`，五天对比）

| 指标 | 11-22 | 11-23 | 11-24 | 11-25 |
|---|---|---|---|---|
| `pic_render` 平均 render_ms | 997 | 1148 | 1048 | 1175 |
| `official_sent` 平均 duration_ms | 2072 | 2134 | 1768 | 1815 |

**渲染和发送五天都没变**。分段计时（166 个出图样本）：

* 渲染段：0.6~3.5s（手机 ARM，Pillow 绘制，冷缓存才这么慢）
* **上传段（render→merged）：median 2.0s / p90 4.0s / max 13.0s**，且 11-25 均值
  从 2.0s 涨到 3.2s
* 发送段：median 2.0s

### 13s 尖峰的真相

```
23:26:06 pic_render cache=miss render_ms=747.9
23:26:11 material_net_retry step=prepare error=NetworkError   ← 等 5s
23:26:17 material_net_retry step=put     error=ConnectError   ← 再等 6s
23:26:19 material_uploaded
```
11s 全是「连不上」在等系统 TCP 超时；而 0.4s 后重试一次就通。同类证据：昨晚
11 条 `channel_send_failed ... NetworkError duration_ms=5026`。

### 今天改的三处

1. **人物卡接入渲染缓存**：`render_panel()` 原先自己重写了一遍 `_style_for` +
   `pic.render`，是**唯一绕过 `_RENDER_CACHE`** 的入口（最高频的那张）。改为
   `return await _render_list("doupo", data, CARD_NAME, qq=p.get("qq"))`。
2. **PUT 连接超时单独压到 3s**（`_PUT_TOTAL_TIMEOUT=30 / _PUT_CONNECT_TIMEOUT=3`）
   —— 只压 connect，上传本身仍留 30s 给弱网上行。黑洞地址实测 3.0s 认输。
3. **复用 httpx.AsyncClient**（按事件循环持有）。实测每请求 **188ms → 41ms，
   单张省 ~147ms**（省掉 DNS+TCP+TLS）。

### 新增观测（下一轮用数据说话）

`ensure_material` 现在打 `material_timing prepare_ms= put_ms= complete_ms= total_ms= bytes=`。
若 put_ms 占大头 → 下一步压 PNG 体积；若 prepare/complete 占大头 → 接口 RTT，另议。

### 明确排除的

* 渲染缓存本身没坏：手机实测 `panel 903.9ms → 2.6ms`、`item 715.1ms → 0.6ms`。
* 「图+按钮合并」没坏：`kind=merged_card` 自 11-21 起就是常态（164/173 条），
  不是昨天按钮改动引入的。
* 手机不是资源瓶颈：load 0.29、free 4607/5651MB。

## 八、力竭真机验收通过 + 出卡提速第二版（数据驱动，ff41bf5）

**力竭真机验收（用户 09:56 实操）**：自动爬塔力竭后存档 `hp=76 / 上限 1520 = 5.0%`，
`tower_checkpoint` 仍 14（一层没过）。之前 09:19 那次是 676/1520=44.5%（没打起来或
未力竭），不是 bug —— **判据必须是「力竭那一刻正好等于体力×5%」**，只看"没满血"会误判。

**真机三张卡 `material_timing`（同机同接口）**：

| 时间 | 卡 | bytes | prepare | put | complete | total |
|---|---|---|---|---|---|---|
| 09:50 | 焚血散详情 | 118569 | 3262 | 339 | 1040 | 4642 |
| 09:55 | 人物卡 | 178557 | 637 | 348 | 1040 | 2026 |
| 09:57 | 人物卡 | 177156 | 1606 | 339 | 1120 | 3066 |

- `put_ms` **恒定 339~348** → 170KB 上行 0.34s，**压 PNG 零收益**（§7 第一条划掉）。
- `complete_ms` **恒定 1040~1120** → 不是网络抖动，是「一次 complete POST + 一次 LRU
  DELETE」。`MAX_MATERIALS=92` 且常用态就在 92 张 ⇒ **每张新卡必然淘汰一张旧卡**，
  每张冷卡白等约 1 秒删上一张。
- `prepare_ms` 637/1606/3262 抖 → 尾延迟，重试治不好，只能对冲。

**调研结论**：官方「素材管理」文档确认 `complete` 返回 `qqbot-media://` 引用，**不是公网
URL** ⇒ "自建 URL 绕过上传"这条路不存在；社区最成熟实现 `yunzaijs/alemonjs-load-yunzai`
靠「命中即直发引用、绝不调 prepare」+「淘汰按 7 天未用/次数最少」省时。

**改动 ff41bf5**（`channel/media_asset.py`）：
1. LRU 淘汰只摘记账，id 进 `_PENDING_DELETE`，后台 `_drain_evicted_loop` 补删，本次绝不
   await；中途取消只留队列（先 peek 后删再摘）；残留孤儿由 `_quota_vacancy` 兜。
2. prepare 加 `_PREPARE_HEDGE_AFTER=1.2` 对冲：超时未回并发补发第二个取先成功者；
   快路径行为不变。多出的 upload_id 不占配额（配额算 complete 后的 image_id）。

不许凭空删、慢首发必须对冲(<2.0s 且 2 次)、快路径不许多发、全失败必须抛。

## 13:31 线上事故：官方通道连接超时 → 整条回复静默丢失（用户「报错了」）

**现象**：13:30 连发两张卡（`doupo:flames` 300KB、`doupo:panel` 184KB）全丢。日志

**定位（证据化）**：失败耗时精确卡在 **5033 / 5031 / 5025 ms**，而 nonebot 驱动 httpx 默认
`DEFAULT_TIMEOUT = Timeout(total=None, connect=5.0, read=30.0)`（`nonebot/internal/driver/model.py:25`）
⇒ 是**连接阶段**超时，不是服务端慢、不是报文错。事故后手测 `api.sgroup.qq.com`
**20/20 次 TLS 握手成功、p50 140ms、0 失败**，且该域按 DNS 轮询到过 101.91.19.174 与
61.151.231.145 两个不同边缘 IP ⇒ 某条边缘节点瞬时不可达（5GHz 手机重连易钉在坏边）。
**非本轮改动引入**：12:17 也失败 2 次（间隔 5s），11-25 晚 19:45~22:09 累计 11 次，属历史间歇。

**修复**（`channel/official.py` + `channel/media_asset.py`）：
1. `_is_connect_phase_error()` 顺 `__cause__/__context__` 判底层是否 ConnectError/ConnectTimeout/
   gaierror（适配器把它包成 `NetworkError("API request failed") from e`，只看外层类名会漏判）。
2. `send()` 段级重发：`_SEND_CONNECT_RETRY=2`，退避 0.6s×n，**每次换新 msg_seq**（同 msg_id 重复
   seq 会被平台按去重拒收 40054005）；被动窗口剩余 <20s 时不再重试。**读/写超时一律不重发**
   ——那可能是「服务端已处理、回包丢了」，重发会真的给玩家发两条。
3. `media_asset._retry_net(..., retries=)`：prepare 由 1 次放宽到 2 次（`_PREPARE_RETRIES`）。
   依据：prepare 幂等、未 complete 的上传 4h 自然失效不占配额；连接失败请求没到服务端。
   PUT 不放宽（单次总超时 30s，再多会吃光被动窗口）。

attempts==[1,2,3]；读超时→只发 1 次并如实 ok=False）；变异反证 `_SEND_CONNECT_RETRY=0`
